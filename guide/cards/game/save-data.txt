# Saves and settings that survive a new build and a private window

All eight games keep something: settings, progress, best marks, a wardrobe. Each wrote its own `localStorage` code first, and the same three things went wrong. A private window or a blocked site throws on access. A new build reads an old save of another shape. A full storage refuses a write. The kit's save store handles all three:

```js
import { createSaveStore } from '@egret/engine/kit';
import { browserSaveStorage } from '@egret/engine/web/kit';

const save = createSaveStore({
  key: 'my-game',
  version: 2,
  defaults: () => ({ best: 0, settings: { quality: 'auto', lang: 'auto', volume: 0.8 } }),
  migrations: { 1: old => ({ best: old.best ?? 0, settings: { quality: 'auto', lang: 'auto', volume: 0.8 } }) },
  storage: browserSaveStorage(),
  onProblem: problem => console.warn(problem.kind),
});
save.update(data => { data.best = Math.max(data.best, score); });
```

The store keeps `{ version, savedAt, data }`, brings older saves forward step by step, keeps a save it cannot read under `<key>.unread` instead of losing it, and returns `false` instead of throwing when a write is refused.

Rules:

- Raise `version` and add a migration whenever the shape changes. LoveElective moved dyes from equipped pieces to a per-character table and had to infer them from old saves; a migration step does that once, in one place.
- A save from before versions existed is bare data. SnowTemple wraps it as version 1 before opening the store.
- Check values read back, not only the shape: FPS clamps a saved sensitivity to its range. `shapeOf(defaults, rules)` gives a `validate` that holds a save to the shape of its defaults and to rules by path, and fills the fields an older save lacks; twelve games wrote the same by hand.
- Keep settings (quality, language, volume, key bindings from `input.saveBindings()`) apart from progress, so resetting a run does not reset the controls.
- Save at calm points (a level end, a menu), not every frame.
- Give a large or precious save a way out: `save.export()` as a file and `save.import(text)`, as Wulin offers when storage is refused. Saves too large for local storage go to `openIndexedDBSaveStorage`.
- Test migrations in Node with `createMemorySaveStorage()`: write an old save, open the store, check the data and that the old text was not lost.
