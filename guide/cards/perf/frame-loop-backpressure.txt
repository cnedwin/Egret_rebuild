# Let the engine's frame loop pace drawing

A Host holds only a few unfinished frames. A loop that draws on every `requestAnimationFrame` regardless gets `FRAME_RENDER_FAILED` with a cause ending in `_BACKPRESSURE`. A loop that hands the clock a whole hidden-tab pause gets `CLOCK_DELTA_LIMIT`.

Use the engine's loops instead of writing one:

| Game | Loop |
| --- | --- |
| `play`, `play3d`, `createBrowserGame`, `createWorld3DApp` | built in |
| World3D with its own renderer | `createWorld3DView(engine, scope, { renderer, scene, camera, onUpdate, onError })`, then `startWorld3DLoop(engine, onError)` |
| 2D shared Host made by hand | `createBrowserFrameLoop` from `@egret/engine/web/loop` |

All three large games use `createWorld3DView` and `startWorld3DLoop`: the Engine clock calls `onUpdate`, then the view draws.

Rules:

- Step the rules inside `onUpdate` with the seconds it is given. Never call `setTimeout`, `setInterval` or a second `requestAnimationFrame` loop for game time.
- The loop skips a draw while the Host is busy and splits long gaps into steps the clock takes. Keep both behaviours; do not "catch up" by drawing twice.
- Pass `onError`. A failed loop stops; show the failure and a reload button, as FPS does, rather than a frozen picture.
- In devtools, `frames-skipped` (a tenth or more of display frames drew nothing) and `host-backlog` (two or more frames pending) mean the GPU side is behind: draw less per frame, not more often. `host-failed` and `host-not-active` name the Host's own failure or state in `subject`.
- `WEBGL2_CONTEXT_LOST` and `WEBGPU_DEVICE_LOST` are the browser taking the device. Frames are refused until it returns; do not treat them as game bugs.

```js
import { createBrowserFrameLoop } from '@egret/engine/web/loop';
const loop = createBrowserFrameLoop({ engine, host, frame: frameOptions, update: dt => game.update(dt) });
loop.start();
```
