# Prepare shader programs during loading, not at first use

The first time a material variant is drawn, WebGL2 links its program. On the measured machine (Edge 157, RTX 5090 Laptop, ANGLE D3D11) one link took 179 ms; prepared, the same change took 4.1 ms. FPS saw two stalls of about 130 ms when the first supply crate appeared. Jelly Pandas and FPS each needed a fix commit for this, so expect it in any game with many materials.

A variant is the material plus how it is drawn: fog, shadows received, transparency, instancing, the mirror pass. A crate drawn as an instance and the same crate drawn alone are two programs.

```js
await renderer.preparePrograms([
  { mesh: crate, material: crateMaterial, receiveShadows: true, fog: true },
  { mesh: crate, material: crateMaterial, pass: 'shadow' },
  { mesh: glow, material: additiveMaterial },
]);
```

Rules:

- Call `renderer.preparePrograms` while the loading screen shows, for every variant an interaction will need: effects, pickups, the first enemy, hurt effects. Pass the mesh that will be drawn and the material it will use.
- For a `CustomShader3D` effect, prepare with a detached mesh and the effect material. Keep the shader's `key` stable; changed GLSL needs a new key.
- Mirror passes have their own variants. On WebGL2 pass `reflection.createPass(camera, hidden)` as `reflection` in the descriptors.
- Where a variant is hard to describe, draw it once off screen during loading, as FPS's `view.warm` does (a fixture placed far below the map) and as Jelly Pandas does with zero-scale meshes inside the title's mirror pass. Do not advance game time while doing it.
- Prepare again after the context is restored.
- Check it: the devtools `recent-hitch` hint, or a frame-interval log of the first ten seconds of play, should show no frame over about two budgets.

WebGPU builds its pipelines differently; Jelly Pandas reuses instanced pipelines and prepares first-use effects on the title for the same reason.
