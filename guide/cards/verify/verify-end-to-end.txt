# Verify a game end to end and record what was checked

Four layers, cheapest first. Each catches what the one before cannot.

1. **Rules in Node.** `node --test` against the sim (see `sim-view-split`). Seeded, fast, run on every change.
2. **Whole runs in Node.** A stand-in player plays N seeds to the end and prints time, result and the slowest step: `node tools/headless.mjs 5 1` in FPS, `runHeadless` from `@egret/engine/kit` in a new game. A balance change is judged on these numbers.
3. **Headless browser.** `node vendor/egret.mjs check` checks files; `node vendor/egret.mjs verify` checks launch, drawing, frames, input, sound and engine warnings. Ordinary verify waits up to 60 s per startup for visible, nonblank, running content (including script reload). Set `--startup-timeout 120000` in ms. The optional game-owned `window.egretGame.ready` boolean vetoes readiness while false; true still needs drawing and frames. Timeout fails startupReady; unmarked loading screens can appear ready. `verify --screens` checks nine viewport profiles (including `foldable-cover-wide`, the measured 873 × 325 Fold7 cover-screen landscape browser viewport) for notches, small or overlapping targets and screenshots. Add `--play test/play.mjs` for a route on each. Await uniquely named `player.checkpoint('rules')` at stable states; a failed checkpoint or script fails that screen. See screen-fit.md for fresh-control and responsive-coordinate details. A large game can expose read-only status and an `?auto=1` stand-in player.
4. **Real devices.** At least one desktop and one phone, through the normal title screen with real input, to the end of a run. Software rendering in a headless browser says nothing about frame rate.

Record the result in the game's STATUS or README, the way FPS does:

- the engine pin, the device and GPU, the browser and version, the backend, the viewport size, the quality, and the input used;
- what was measured (run time, average fps, p95 and worst frame) and what was not (FPS lists WebGPU, native fullscreen, difficulty and listening as outside its pass);
- known issues as a table of issue and effect, kept current, with solved problems moved to their own list.

Rules:

- Keep claims apart: "tests pass", "played to the end headless", "played on device X" are three statements.
- A number measured before a change is history after it. FPS marks its earlier full-run numbers as a baseline from before an art change.
- When the stand-in player skips a feature (FPS's never searches crates), the automatic run does not cover it; say so.
- Note the pin with every number, since an engine refresh can move it (see `vendor-engine`).
