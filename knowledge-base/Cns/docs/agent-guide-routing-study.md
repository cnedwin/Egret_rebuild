# 《暴雨渡口》：两种白鹭入口能让 Agent 找到什么、做出什么

[English](../../en/docs/agent-guide-routing-study.md) | 简体中文 · [原始首稿、资料读取和录像](https://raw.githubusercontent.com/cnedwin/Egret_rebuild/main/guide/studies/rainstorm-ferry.zip)

新首页提供四条直达入口，文件少了 8,490 个 UTF-8 字节。工具可用时，新入口的作者找到了三张卡和一份图形参考，曾把中间稿压到字节上限以内，但在交稿前超时。最初受工具审批限制的一轮，产生了两份可玩的开场。

## 工具可用时的对照

| 结果 | 旧入口 | 新入口 |
| --- | --- | --- |
| 作者实际打开的参考 | 首个可玩动作、动作反馈 | 首个可玩动作、2D 几何预算、动作反馈、Graphics |
| 初始提示加实际收到的参考正文 | 34,991 + 4,647 = 39,638 字节 | 26,501 + 16,923 = 43,424 字节 |
| 生成中主动计数 | 无 | 25,883 → 24,248 → 23,766 字节 |
| 最终交稿 | 295.633 秒交稿，26,546 字节，超出 2,546 字节 | 480 秒内未交稿 |
| 前 20 秒 | 点击货箱、甲板标记和舵轮。第 11 秒货箱已装船，第 13.4 秒可见渡船带着货物离开码头。 | 最终回答为空，无游戏可供录制。 |

中间稿的字节数来自计数工具。交稿时还要核对最终文件大小，并确认游戏可运行。这一对实验中，首页缩短了初始提示，但新入口的作者读了更多资料，所以提示和资料正文合计更长。这次可以确认它找到了哪些内容、怎样使用计数工具；两组最终玩法未能在工具可用的条件下完成对照。

## 首轮：工具审批挡住资料读取

旧入口的作者未请求资料，源码为 29,650 字节，超出 5,650 字节。新入口的作者主动找到动作反馈、首个可玩动作和 2D 几何预算三张卡，但三次读取都在到达工具前被运行器拒绝。该组原稿为 23,809 字节，距离上限还剩 191 字节。

两份首稿都在第 11 秒前让货箱上船，随后带着货箱驶离码头。旧入口稿可以直接点击货箱、甲板货位和驾驶台，第 13.50 秒已经离岸。新入口稿通过同一个屏幕按钮依次搬箱、装船、解缆、开船，第 18 秒可见船开始离开码头。两份首稿都完成了开场，这一轮也记录了工具受限时 Agent 能找到哪些链接。

## 对照方法

两组收到同一个新需求：“做一款名叫《暴雨渡口》的 2D 小游戏。暴雨就要来了，玩家要把第一箱货装上渡船，再让船驶离码头。” 两组的 HTML、起始游戏模块和白鹭 2D 引擎文件逐字节一致，引擎来自 `5792d800`。两组都用 `gpt-6.2-sol` 中等推理，各产出一次最终回答，限时 480 秒，游戏源码上限为 24,000 个 UTF-8 字节。起始 HTML 的标题同步换成了新游戏名。

旧入口来自 `ff93e89e`。新入口将四条创作或排查路径放在可运行的最小示例前，链接完整游戏，并扩展首个动作和 2D 绘制指南。每组的提示只附各自的入口，使用相同工具打开对应快照里的参考文件和计算实际字节数。初始提示加工具实际返回的参考正文合计上限为 96,000 字节，单次读取最多 18,000 字节，最多调用工具 18 次。作者自行选择资料，交付前也可以计算源码字节数。只有工具返回了正文，记录才算一次成功读取。每份首稿都在封存后才运行。

每份有录像的游戏都在 Windows Chrome for Testing 157 的新会话运行，使用 SwiftShader WebGL2 和 960 × 540 视口。操作方只看随机标签与画面提示，在第 4、8、12、16 秒各最多操作一次。每段录像都从打开网页开始。每轮每种入口只生成一次，使用自动化输入，未覆盖真人初次体验。
