# 为 Android 游戏选择脚本宿主

[English](../../en/docs/android-project-player-v8.md) | 简体中文

用 [Android 游戏项目播放器](android-project-player.md)导出的游戏，可以使用手机上的系统 WebView，也可以把 V8 随 AAR 一起打包。三种构建共用 Rust GLES3 渲染器、资源作用域和 Android 游戏视图。在构建 AAR 时选择脚本宿主。同一游戏仍可单独打包，或嵌入已有应用的 Activity。

| 构建参数 | 脚本环境 | 最低 Android API |
| --- | --- | ---: |
| `webview` | 已安装的系统 WebView、本地 HTML 入口及浏览器 API | 26 |
| `standard` | V8 15.7.112.19，带 JavaScript `Intl` 和 ICU 语言数据 | 29 |
| `trimmed`（默认） | 相同版本的 V8，构建时去掉 `Intl` 及其 ICU 数据 | 29 |

游戏依赖 DOM 或优先控制下载体积时，可用系统 WebView。需要自带虚拟机，且使用 `Intl` 进行本地化格式化或排序时，选标准 V8。三种宿主均可调用 Android 字体显示中文。两种内置 V8 使用 Javet 6.0.3 的 arm64 构建。依赖版本、哈希及许可见[来源清单](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/android/v8-provenance.json)。

## 构建与运行

按照项目播放器文档准备工具链后，在仓库根目录运行下列命令。对比构建时使用同一份游戏工程和渲染器。各配置的依赖和许可文件下载齐备后，缓存可离线复用。

```sh
node runtime-sdk/android/player/build-aar.mjs --v8-profile trimmed --v8-cache out/v8-cache --out out/player-trimmed.aar
node runtime-sdk/android/player/create-app.mjs --aar out/player-trimmed.aar --project runtime-sdk/examples/moon-herbarium --esbuild /path/to/node_modules/esbuild --layout embedded --id org.example.herbarium --out out/herbarium-v8
gradle -p out/herbarium-v8 assembleDebug
```

构建其他配置时，相应更换 `--v8-profile`、AAR 文件名和导出目录。生成的应用按所选库设置最低 Android API。V8 版 AAR 含虚拟机、Java 绑定、供应用压缩时使用的保留规则及分发许可。生成的调试 APK 把虚拟机原生库按对齐要求直接存储，AAR 则对同一文件进行压缩。签名 APK、AAR 和应用商店下载体积需分别测量。标准版首次使用时，还会把校验过的 ICU 数据安装到应用私有目录。

## 工程接口与生命周期

内置 V8 在独立线程直接执行导出的 `game.js`。项目可以使用游戏时钟、定时器、资源取消、舞台输入、原生文字编辑、音效和二进制帧提交。需要执行本地 HTML 脚本或直接访问 `document`、`Image` 等浏览器对象的游戏，应使用系统 WebView。播放器从安装包读取项目资源。需要加载远程内容时，由应用另行接入。播放器面向随包分发的可信游戏脚本。

二进制关卡可用 `services.assets.readBytes(path, signal)` 读取，三个宿主返回相同的字节。通过 `await services.assets.readText(path, signal)` 可以读取清单中的关卡或对白文件。三种宿主使用相同的 UTF-8 解码规则，并在游戏关闭时取消未完成的读取。[Android 游戏项目播放器指南](android-project-player.md)给出了按关卡内容选择图集帧的示例。

项目可通过可选的 `services.raster` 解码已声明的 PNG，测量文字宽度，或把文字绘入纹理。三种构建使用同一套 Android 解码器和系统字体。每页最多 1,048,576 个像素，每边最多 4,096 像素。在加载资源或文字变化时准备纹理，准备阶段的图像传输采用 Base64。逐帧命令使用二进制缓冲区。每个 V8 游戏会话独占一个线程和一个隔离实例。收到 `onClosed()` 后，宿主可打开下一款游戏，此时上一会话的资源和虚拟机均已清理。

## 如何测量播放器

嵌入示例支持在 `adb shell am start` 启动参数中传入 `--ez egret.timing true`。Activity 诊断输出的 `timing` 对象记录预热 30 帧后连续 180 次成功提交。启动时间从进程启动或视图创建开始，到主线程收到首次原生提交成功的回调结束。帧间隔指连续两次回调之间的时间。`dispatchToEnqueueUs` 包含调度、脚本生成和传输，`enqueueToCallbackUs` 包含 GL 队列和主线程接收回调的时间。跨宿主比较可使用从派发到入队的时间。WebView 在 JavaScript 内计时，内置 V8 的生成耗时还包含 Java 调用 V8 方法的开销。V8 可单独记录显式缓冲复制耗时。WebView 的 Java 桥内部转换无法单独计时，该项记为不可测。GPU 实际执行、屏幕呈现和人耳听感需要另行测量。

## Fold7 实测

2026 年 11 月 19 日，在 Android 17、Adreno 830 的同一台设备上运行《月下药铺》。三份调试 APK 包含逐字节相同的六个游戏文件及 Rust 渲染库。每个宿主先完成一次独立的全新安装测试，再轮换顺序各测三次进程冷启动。后者复用文件缓存，标准 V8 的 ICU 已在私有目录内。下表为三轮的中位数。PSS 包含可归属的 WebView 渲染进程。

| 宿主 | APK（MiB） | 首次提交（ms） | 提交间隔 p95（ms） | 派发至入队 p50（ms） | PSS（MiB） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 系统 WebView | 1.69 | 332.1 | 16.18 | 3.18 | 237.2 |
| 标准 V8 | 69.27 | 250.9 | 8.90 | 1.01 | 216.3 |
| 裁剪 V8 | 61.80 | 250.8 | 8.89 | 1.01 | 216.9 |

三种宿主都完成配药、列表滚动、系统键盘编辑及音效的启动和释放。排除移动角色经过的区域后，各宿主的 2,038,968 个静态游戏像素逐点相同。每个游戏切后台再返回后恢复了 EGL 上下文，静态区域与切后台前一致。关闭时每个宿主均归还了 14 份逻辑纹理，随后重新打开游戏。另一个开启 R8 压缩的裁剪 V8 应用通过了独立的真机启动、关闭和再打开。

原始回放基准使用独立的 EGR1 固定场景。《月下药铺》的数据仅覆盖以上三种实时脚本宿主。[本轮设备记录](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-project-v8.json) · [原生命令回放对照](runtime-sdk-v8-fold7.md)

## 在同一款游戏里对照原生命令回放

生成的嵌入示例可在开启调试的应用中选择三种测量模式。`capture` 让游戏按固定逻辑时间运行前 210 次提交，第 n 帧的时间为 `n × 1000 / 120` 毫秒。录制器保存成功提交的 2D 命令，或带有序绘制列表和 2D 叠加层的 World3D 场景，以及该帧使用的未预乘 Alpha 的 RGBA 纹理页。绘制可以共用驻留几何，录像也记录纹理的替换和移除。完整记录写入应用私有目录后，以原子操作发布。每份记录最多 64 MiB，最多包含 4,096 个纹理页版本。每个应用保留最近一次完整记录。若新录制替换了旧文件，回放会在绘制前核对请求的摘要。

全部由完整命令包组成的录像继续使用原 EGRP v1 布局和校验规则。含驻留几何引用的录像采用 EGRP v2，需要支持 v2 的播放器。首帧与末帧均可独立绘制，中间的 World3D 帧可引用前一帧的网格，同时保存自身的相机、有序绘制列表、HUD 和纹理页版本。加载时，播放器检查前后帧的依赖以及每一帧展开后的大小。恢复时只从已存几何中组装所需的那一帧。

`live` 以相同逻辑时间运行游戏，跳过录制。`replay` 预加载经校验的记录，将相同命令直接提交给原有 GLES3 渲染器，全程无需启动脚本虚拟机。各模式均忽略游戏操作，完成后停在第 209 帧，便于逐像素比较。EGL 上下文重建后，渲染器恢复纹理页并重绘末帧。如果回放途中丢失上下文，播放器会从录制时的几何定义重建下一张尚未确认的帧，随后恢复增量提交。录制途中若发生中断，须重新录满后才会替换原有完整录像。录制、实时计时和回放计时分别启动。回放的启动时间包含读取和校验，下表使用的驻留内存也包含停在末帧时仍保留的预加载记录。

以应用标识为 `org.example.herbarium` 的嵌入示例为例，先执行：

```sh
adb shell am start -S -n org.example.herbarium/org.egret.example.LibraryActivity --es egret.benchmark capture
adb shell dumpsys activity org.example.herbarium/org.egret.example.LibraryActivity
```

等 `benchmark.complete` 为真后读取 `benchmark.sha256`。该摘要覆盖录像的有效载荷，计算时不含末尾 32 字节的 SHA-256 校验值。各轮之间保留应用数据。以下命令分两次执行，每次完成后读取 Activity 诊断输出。将 `CAPTURE_SHA256` 替换为实际得到的小写摘要。

```sh
adb shell am start -S -n org.example.herbarium/org.egret.example.LibraryActivity --es egret.benchmark live --ez egret.timing true
adb shell am start -S -n org.example.herbarium/org.egret.example.LibraryActivity --es egret.benchmark replay --es egret.replaySha256 CAPTURE_SHA256 --ez egret.timing true
```

原生回放没有脚本生成或脚本到宿主的复制阶段。跨模式比较可采用从派发到进入渲染队列的耗时，以及相邻提交成功回调的间隔。各模式预热后开始采样。这两项指标包含宿主调度与队列等待。GPU 执行和屏幕呈现需要单独采集。

### 固定负载的 Fold7 结果

每组四次进程冷启动，轮换测试顺序，让每种模式在四个位置各出现一次。每次均预热 30 帧，再记录 180 次提交，共 2,880 个样本。先按每轮样本计算 p95，再取四轮各项指标的中位数。PSS 在持有末帧时读取，包含实际归属该应用的 WebView 渲染子进程。

| 模式 | 进程启动到首次提交回调（ms） | 提交回调间隔 p95（ms） | 派发到入队 p95（ms） | 驻留 PSS（MiB） |
| --- | ---: | ---: | ---: | ---: |
| 系统 WebView | 329.5 | 15.885 | 7.221 | 222.1 |
| 标准 V8 | 247.9 | 8.830 | 2.291 | 202.0 |
| 裁剪 V8 | 244.3 | 8.788 | 2.296 | 200.4 |
| 原生命令回放 | 75.2 | 8.812 | 0.012 | 118.4 |

210 帧中每帧绘制 81 个四边形。去掉帧号后，命令内容有 26 种变化。原生回放的派发耗时很低，两个内置 V8 的提交间隔 p95 与回放接近。对这个场景，WebView 从派发到入队的时间值得优先分析。该差额同时包含线程调度、命令生成和传输，无法单独归因于某一次复制或 GPU 执行。

三种脚本宿主各自录出的文件逐字节相同，大小均为 2,483,048 字节。四组末帧的 2,073,600 个像素完全一致，包括移动角色。取原始角色图集的 280 个不透明采样点逐一核对，四组采样均与原画一致。每组重建 EGL 后再次绘出相同画面，关闭时合计上传和释放纹理各 8 次。调试版拒绝摘要不符的回放，开启 R8 压缩的正式版按普通游戏路径运行。[四组实测及原始样本](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-project-replay.json)

### Galaxy Z Fold7 上的 WebView 命令传输

上表的派发到入队 p95 为 7.221 ms。为定位耗时，在同一台 Fold7 上用原 WebView 通道冷启动《Moon Herbarium》三次，每次沿用 30 帧预热，再记录 180 帧。分别取每轮派发最慢的 9 帧，从 JS 调用到 Java 收到数组占其平均派发耗时的 65.2%–69.5%。该区间包含参数转换、跨进程传递和线程调度。

| 同一组最慢 9 帧的平均耗时（ms） | 第 1 轮 | 第 2 轮 | 第 3 轮 |
| --- | ---: | ---: | ---: |
| 派发到 JS 开始执行 | 1.009 | 0.951 | 1.149 |
| 游戏生成命令 | 0.733 | 0.800 | 0.900 |
| 创建视图与长度校验 | 0.022 | 0.000 | 0.011 |
| JS 调用到 Java 进入桥接方法 | 4.422 | 3.719 | 5.224 |
| Java 校验和捕获帧快照 | 0.038 | 0.026 | 0.033 |
| 等待 UI 线程执行 | 0.152 | 0.196 | 0.180 |
| UI 线程开始执行到入队计时点 | 0.017 | 0.010 | 0.019 |
| 派发到入队总计 | 6.392 | 5.702 | 7.515 |

每轮采集前后各用 24 次往返对齐 JS 和 Android 时钟。对每次往返得到的偏移区间，两端各放宽实测 JS 时钟粒度 100 µs 和取整余量 1 µs。每批取 24 个区间的交集，以各次往返中心的平均时刻为基准，在两批交集中点之间做线性插值。端点偏移区间半宽为 42.6–94.4 µs。540 帧重算的派发总耗时与原计时器逐帧相差最多 1 µs。很短的 JS 操作可能落在同一个时钟刻度内。[逐帧时间戳与时钟校准数据](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-webview-bridge-diagnostic.json)

当命令视图的偏移和长度都按 4 字节对齐时，WebView 播放器把每 4 个字节作为一个有符号 32 位整数发送。场景中每帧 5,208 字节，通过同步桥接只需传递 1,302 个数组元素。Java 按设备字节序还原原始命令，在原位置获取纹理页快照，再向 UI 线程投递。其他切片沿用逐字节通道。

关闭分段探针后，在同一台手机、WebView 157 和 GLES3 渲染器上做 6 对冷启动复验，AB 和 BA 交替。各轮派发到入队 p95 的中位数从 6.562 降至 3.593 ms。逐对计算，耗时降幅的中位数为 2.894 ms，相对降幅的中位数为 44.1%，6 对均有改善。采集前约定的门槛为至少 4 对改善、中位降幅至少 0.500 ms 且至少 10%。提交回调间隔 p95 的中位数从 11.024 降至 8.930 ms。本次计时覆盖宿主线程，GPU 执行、屏幕呈现和功耗仍待分别测量。

两版 210 帧生成的完整命令与纹理记录逐字节相同，均为 2,483,048 字节。EGL 重建前后，固定末帧的 2,073,600 个像素全部一致。两版在两个上下文中各上传和释放 8 张纹理，均通过独立的普通关闭和重开验证。[成对样本、包身份与一致性结果](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-webview-bridge-pairs.json)

### Galaxy Z Fold7 上的内置 V8 命令生成

沿用 #386 的《Moon Herbarium》，每次启动按固定逻辑时钟提交 210 帧。标准和裁剪 V8 在同一部手机上各做三轮诊断，记录帧号 30–209。六轮中，耗时最大的单个步骤都是四边形的 EGR2 编码，占每轮最慢 9 个派发帧平均总耗时的 24.7%–30.8%。显示树捕获排在第二。

下表先在每轮取同一组最慢 9 帧的平均耗时，再列出同一配置三轮的范围，单位为毫秒。游戏命令生成包含从 Java 调用 V8 及返回的耗时。

| 宿主 | 派发到工作线程 | 游戏命令生成 | 其中 EGR2 编码 | 从 VM 复制结果 | 校验与快照 | 等待 UI 线程 | UI 处理到入队 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 标准 | 0.108–0.159 | 0.959–1.941 | 0.377–0.751 | 0.126–0.277 | 0.008–0.017 | 0.089–0.161 | 0.008–0.011 |
| 裁剪 | 0.129–0.164 | 0.949–1.046 | 0.348–0.421 | 0.122–0.128 | 0.008–0.009 | 0.136–0.142 | 0.010–0.011 |

JS 内部 8 个标记点、工作线程和 UI 线程都读取同一 Android 单调时钟。每轮采集前后各连续调用 96 次空标记，测得相邻标记间隔中位数分别为 2.8 µs 和 17.1–23.3 µs。分段数据保留这部分开销。按时间戳重算派发、生成和复制，与原计时器逐帧相差最多 0.5 µs。[逐帧时间戳及探针校准](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-v8-command-stages.json)

第一种实现将四边形字段直接写入命令包。标准 V8 的配对生成耗时降幅中位数为 72.5 µs（9.0%），裁剪 V8 为 90.5 µs（10.8%），都低于 100 µs 的门槛。第二种实现沿用相同门槛，两种配置分别重新做了 6 对独立比较。[第一种实现的完整数据](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-v8-direct-writer-pairs.json)

同一条不可变引擎命令再次出现在相同绘制位置时，播放器保留一份私有的 64 字节 EGR2 记录。后续帧只有在材质、视口、图集映射、纹理尺寸和驻留槽都匹配时才复用该记录。绑定改变时重新校验和编码。每帧都在变化的位置只记住上一条命令的身份。缓存条数以当前绘制数量为限，记录字节最多 256 KiB，另有元数据。编码失败或工程关闭时清空缓存，每个返回的命令包都独立持有其字节。重新导出改变了 game.js 中的 SDK 代码。每种配置均沿用原 AAR、V8 二进制、原生渲染器、游戏源码及资源。

正式测量关闭分段探针。两种 V8 在同一台 Fold7 上分别做 6 对冷启动，交替先跑原版和候选版。每轮按最近秩计算 p95，下表为 6 轮 p95 的中位数，单位为毫秒。另用同一份命令记录冷启动 3 次原生回放，派发 p95 的中位数为 0.012 ms。回放直接读取命令，无脚本生成与 VM 复制。

| 宿主 | 构建 | 生成 p95 | 复制 p95 | 派发到入队 p95 | 提交回调间隔 p95 |
| --- | --- | ---: | ---: | ---: | ---: |
| 标准 | 原版 | 0.834 | 0.142 | 1.276 | 8.727 |
| 标准 | 复用记录 | 0.702 | 0.156 | 1.111 | 8.824 |
| 裁剪 | 原版 | 0.851 | 0.141 | 1.262 | 8.711 |
| 裁剪 | 复用记录 | 0.759 | 0.160 | 1.151 | 8.754 |

标准 V8 有 6/6 对改善，配对绝对降幅和相对降幅的中位数分别为 0.152 ms 和 17.8%。裁剪 V8 有 6/6 对改善，配对绝对降幅和相对降幅的中位数分别为 0.114 ms 和 13.2%。每种配置独立验收，要求至少 4 对改善、配对绝对和相对降幅中位数至少为 0.100 ms 和 10%。同时要求派发到入队 p95 的配对中位耗时持平或改善，提交回调间隔 p95 最多回退 0.250 ms。本次记录宿主线程时间，GPU 执行、显示呈现和功耗需独立测量。

按对计算，标准和裁剪 V8 的派发到入队 p95 分别缩短 0.166 ms 和 0.117 ms。提交回调间隔 p95 分别增加 0.088 ms 和 0.030 ms，均在 0.250 ms 容许范围内。固定末帧时的进程 PSS 中位数分别高出 7.1 MiB 和 4.9 MiB。该轮采集的是进程 PSS 总量；下一节进一步测量了原生分配器和 V8 堆。

两种配置的原版和候选版均复现了 #386 完整命令及纹理记录，2,483,048 字节逐字节相同。EGL 重建前后，1,080 × 1,920 末帧画面所有像素一致，每版跨两个上下文共上传和释放纹理各 8 次。普通游戏交互、关闭和重新打开也已验证。[成对样本、回放及资源回收记录](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-v8-command-pairs.json)

另在 Windows x64 的 Node 上单测编码器，每种负载用 81 个四边形做 12 对冷进程对照。每帧只改一个四边形时，各轮编码 p95 的中位数从 106.85 降至 18.45 µs。每帧全部变化时，该值从 95.30 升到 110.65 µs。下一节记录了 Fold7 上所有四边形逐帧变化时的实测结果。[桌面编码器对照数据](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/desktop-egr2-record-reuse.json)

### Fold7 全变化四边形与末帧内存

压力场景每帧改变全部 81 个四边形的变换。210 帧间逐位置比较的 16,929 条记录全部变化。两种 V8、两代编码器生成的命令带逐字节一致。八个构建在 EGL 恢复前后得到的 1080 × 1920 实机整幅画面一致，每个构建使用两张纹理，跨两个上下文共上传四次、释放四次。另与理想图对照，实机截图右边缘 22 × 195 区域内有 4,141 个像素不同；各构建间的比较包含这个区域。

每种 V8 各做六对带轻量编码计时的冷启动，再用另一组六对无探针冷启动测量整段生成和派发。表中正数表示 #388 用时增加，数值为每对 p95 差值的中位数。

| 内置 V8 | 编码 p95 变化 | 编码 p95 上升的配对 | 完整生成 p95 变化 | 派发到入队 p95 变化 |
| --- | ---: | ---: | ---: | ---: |
| 标准 | +8 µs（+2.14%） | 4/6 | +170.5 µs | +190.5 µs |
| 裁剪 | +9.5 µs（+2.63%） | 6/6 | +3 µs | +7.5 µs |

裁剪版有一对慢了 330 µs。两种 V8 的编码差值中位数均低于此次采用的 5% 判定线，也小于各自连续空读时钟的典型间隔 19 和 18 µs。裁剪版六对的方向一致，两型的差值均未达到事先约定的实质性编码回退标准。标准版较大的完整生成差值还包含编码以外的工作。[逐帧数据、夹具和像素对照](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-v8-fully-changing-quads.json)

原版与 #388 的《Moon Herbarium》共做 16 次冷启动，四种构建均衡轮换启动位置。在末帧完成约四秒后，标准和裁剪 V8 的进程 PSS 配对中位数分别增加 4.83 和 3.02 MiB。Scudo 原生分配器的驻留内存分别增加约 8.45 和 7.06 MiB，无名可读写映射占用下降，抵消了一部分涨幅。正式构建的图形内存统计分别变化 0 和 −216 KiB。这些数值是固定时点的进程驻留内存。

每种 V8 使用一个同时包含两代游戏脚本的诊断 APK，在同一包名和 UID 下分别冷启动。每次启动内的干预都保留同一游戏、V8 实例、GPU 资源和末帧画面。保留全部缓存，让 Android 分配器归还空闲页，标准和裁剪版的原生堆摘要（分配器私有脏页）差值分别缩小 4,332 和 5,096 KiB，而已分配字节差的变化均不足 1.5 KiB。随后向 V8 发出低内存通知，已分配字节差分别从约 4.09 MB 降至 −0.29 MB、从 3.52 MB 降至 0.26 MB。单独清除 81 条缓存记录（有效载荷 5,184 字节），相对于原版空操作，V8 已用堆的配对中位数约减少 23 KiB，进程 PSS 相对变化分别为 +18 和 0 KiB。原始数据保留了标准版的一对反向结果，以及诊断进程之间图形内存统计的波动。归还空闲页和低内存通知仅用于诊断。[内存分类与配对干预结果](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-v8-record-memory.json)

另在 Fold7 对四个指定应用进程采样原生分配调用栈，两种 V8 均按构建 ID 匹配本地符号文件。取末帧后约四秒前后的两个快照，编译器 Zone 中采样到的未释放内存，标准版新旧相差约 +45 KiB，裁剪版相差 +2.37 MiB。标准版差值小于 64 KiB 的单个采样间隔。每个编码器、每种 V8 各有一条有效记录，部分调用栈无法完整还原，分配器驻留内存还包含已释放页。可以确认这些运行中 V8 编译任务占用了原生内存，无法把整个 PSS 差额归到某一个引擎函数。首轮四条提前截断的记录已排除。[原生分配调用栈及采样边界](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-v8-native-allocation-stacks.json)

最后一组内存对照中，同一进程在末帧静置，然后处理一次常规 V8 任务队列，再进入一次 JavaScript 执行空操作，游戏保持原画面。上述步骤期间，实测 V8 的 malloc 计数保持不变；随后诊断用的低内存通知才使它下降。这次额外处理任务队列没有发现积压。根据这些结果，沿用 #388 编码器和现有宿主调度、内存策略。[空闲任务对照](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-v8-idle-pump.json)

重新对照 #386 原场景，每种 V8 各做六对无探针冷启动。标准 V8 六对的生成 p95 都缩短，配对中位数为 108 µs（12.9%）；裁剪 V8 五对缩短，配对中位数为 127.5 µs（15.4%）。两型均达到原验收线。派发到入队分别缩短 110.5 和 133 µs，提交回调间隔在标准版增加 44.5 µs、在裁剪版缩短 8.5 µs。两种配置均复现原始 2,483,048 字节命令与纹理数据，EGL 恢复前后全幅 1080 × 1920 像素一致，两个上下文的八次纹理上传全部对应释放。[原场景成对复验与恢复结果](https://github.com/cnedwin/Egret_rebuild/blob/main/runtime-sdk/measurements/fold7-v8-quad-recheck.json)
