# 资源核心合同：CPU获取与租约

[English](../../en/docs/resource-core-contract.md) | 简体中文

日期：2026-10-08。状态：experimental 的下一段实现规格，不是渲染后端或资源全产品验收。

本段实现 `engine.assets`，沿用[公共API合同](公共API设计与命名规范.md)的异步获取、类型化引用和 Scope 所有权。它负责 provider 返回的 CPU 值；不承担下载协议、图像/字体/模型解码、GPU 上传、预算/LRU、持久 manifest 或设备恢复。provider 负责自己的网络/解码工作及取消响应，不能把 GPU 在途句柄交给本段同步清理。

## 公共接口

- `createAssetType<T>(name: string, is: (value: unknown) => value is T): AssetType<T>` 建立不可变描述符，按对象身份匹配；同名描述符不自动别名。泛型类型保持不变性。
- `createAssetRef<T>(type: AssetType<T>, id: string): AssetRef<T>` 建立不可变资源引用。非空 ID 是管理器内的稳定身份；同一 ID 不可改用另一个类型描述符。描述符与引用均须由工厂产生，伪造结构在运行时拒绝。
- `engine.assets.register<T>(type: AssetType<T>, provider: AssetProvider<T>): void` 每个类型登记一次。provider 提供 `load(ref, {signal, resourceGeneration, taskId}): Promise<T>` 和同步 `dispose(value): void`；登记时固定回调。每次成功返回的值具有独立的清理所有权，若 provider 共享底层对象，需自行封装引用计数，不能向不同任务返回同一个可销毁对象。
- `engine.assets.acquire<T>(ref: AssetRef<T>, options?: {signal?: CancellationSignal}): Promise<AssetLease<T>>` 由引用推断类型且用该类型的 `is` 对返回值进行运行时验证。关闭、无 provider、伪造引用、类型冲突和取消均通过拒绝 Promise 返回。
- `AssetLease<T>` 提供只读 `value`、`leaseId`、`resourceGeneration` 和幂等 `release()`。release 或管理器关闭后访问 value 抛出 `ASSET_LEASE_RELEASED`。租约绑定来源 Engine，外 Engine 的 Scope 不可接管。
- `engine.assets.invalidate(ref): void` 使该 ID 的当前代际退出后续获取；原有等待者和已交付租约仍引用原代际。下次获取开启新代际，旧结果或旧 release 不得覆盖/删除新代际。
- `engine.assets.dispose(): void` 同步终结管理器：先关闭入口，再取消全部等待、撤销已交付租约、清理已取得值。Engine 在 Scope 和 Stage 清理后、host.stop 前调用它。管理器再次 dispose 幂等；禁止关闭后重新登记/获取。

名字和 ID 不能为空或全空白；不隐式 trim 或改写有效 ID。leaseId/taskId 是管理器内递增正整数，resourceGeneration 是同一 ID 内递增正整数，均不得超过安全整数。它们不是持久工程 ID、deviceEpoch 或跨线程 ACK。

## 获取、取消与清理

同一 ID/类型/当前代际共享一次 provider 调用，每次 acquire 有独立等待和独立租约。首先登记当前 entry 和第一个等待者，再执行 provider，保证同步重入不会重复启动任务。最后一个等待者取消时，且没有已交付租约，先终结并移除当前 entry，再通知 provider 取消。provider 即使不理会取消，迟到值也会被清理且不交付。

signal 仅取消尚未成功交付的本次 acquire。交付和取消按先终态者裁决，成功后解除监听；之后 abort 不释放租约。Scope 先取消等待、再逆序 release 已登记租约，await 之后迟到的租约仍通过 Scope.use 的既有规则清理。

不保留无租约的完成缓存：最后一个有效租约 release 后终结 entry 并清理值；下次 acquire 创建新代际。调用者需要常驻资源时须保持租约。失效只切换未来获取，不强制替换仍被借用的旧值。

load 同步抛错或异步拒绝、类型验证失败/抛错使该代际失败；所有尚在等待的调用收到 `EgretError`，允许后续显式 acquire 重试。验证失败的已返回值也进入清理。所有内部 Promise 链观察拒绝；调用者仍须处理自己得到的 acquire Promise。

entry 终态、映射移除和清理尝试标志必须在取消/provider.dispose/诊断等外部回调前提交；删除映射必须核对 entry 身份。每个成功 load 结果只调用一次 dispose；异常清理记录 `phase: "assets"` 的诊断，Engine 正在关闭时进入 cleanupErrors，但不重试或阻断其他清理。一次调用不等于清理成功；provider 不完成的 Promise 不能靠本段同步关闭证明物理工作已停。

signal 适配器登记/移除监听失败须保留诊断并回滚本地等待，不能留下不可达需求。诊断 observer 抛错不得改变清理进度。类型校验、取消和 disposer 的同步重入必须按上述终态规则处理。

## 验收与来源

用自有 provider 边界和可控 Promise 验证共享、单独取消、最后等待者取消、取消后迟到成功/失败、关闭中重入、代际交错、错误重试、类型校验和 Scope/Engine 集成。另用真实异步 provider 示例运行核心；测试输出只证明本段 CPU 合同，不证明 GPU fence、性能、包体、电耗或迁移成功。

设计输入是本项目[公共API合同](公共API设计与命名规范.md)、[工程规划](工程规划.md)和[异步资源研究记录](../../evidence/async-resource-probe-results.json)。后者的25例为手工交错研究，不冒充本次执行证据。参考链的整体生命周期取消与本 acquire 的等待取消不同。代码独立编写，不复制研究 probe 或第三方实现；既有公开研究的出处和许可保持在原记录中。
