# 显示树扩展性

[English](../../en/docs/display-tree-scaling.md) | 简体中文

工程预览 **0.27.2** 是有界的 CPU 显示树修复，调整挂接验证和子列表直接读取，不新增公共导出或依赖。包保持 private `0.0.0`，协议固定值保持 `1.0`；S080 与 V031 单独登记其验收状态。

## 源码诊断与基线

在源码基线 `d58e624942ec485d66003ec9bb48e5edab6a6374`，`addChild` 的预检和最终验证遍历接收者的既有后代，随后又对整棵树提交绑定。因此，持续向已绑定的平坦容器逐个追加子对象会重复访问旧兄弟，累计遍历呈二次增长。`numChildren` 与 `getChildAt` 复制子列表快照；即使对象位于尾部，分离仍通过 `indexOf` 搜索。

基于既有编译源码、Node.js 24.19.0 的一次本地观察记录以下毫秒耗时。硬件身份未记录，单次观察不构成比较基准。

| 子对象数量 | 构造 | 采集 | 尾部清理 |
| --- | --- | --- | --- |
| 2,000 | 199.83 ms | 2.49 ms | 1.08 ms |
| 4,000 | 976.23 ms | 2.32 ms | 2.46 ms |
| 8,000 | 4,315.14 ms | 12.87 ms | 13.25 ms |

**另一个** 8,000 子对象的子类探针观察到 32,012,000 次可用性钩子调用，精确符合 `N(N+3)/2`。耗时和钩子计数属于独立范围，不能合计；不据此推算后继加速比例。

## 挂接边界

对已绑定接收者，挂接检查接收者及**完整的待挂接子树**，在初始可用性检查后保留接收者自身的可绑定回调，不会重新执行接收者下无关既有后代的可用性钩子。在接收者可绑定回调之前检查 Engine 开放状态；若待挂接钩子关闭 Engine，仍优先返回 `ENGINE_CLOSED`。这项更窄的回调边界是明确约定的行为。**初始未绑定**接收者仍保留包括既有后代的整树预检和最终绑定验证，即使预检钩子在过程中将其绑定，也保持该路径。

子类钩子可能重入并改变任一棵树。可执行回调的预检结束后，挂接必须重新读取当前 Engine 与内部树状态，再以不调用回调的方式检查存活、Stage 根限制、环路及完整待挂接子树的归属。跨 Engine 和绑定不一致仍拒绝。只有最终验证全部成功后才提交绑定及内部分离／挂接；拒绝不会由该操作留下部分绑定或重挂接。钩子的副作用仍属于其自身回调范围。释放与清理所有权继续遵循既有生命周期约定。

## 成本边界

| 操作 | 有界改动及保留成本 |
| --- | --- |
| 向已绑定接收者追加 | 避免重复访问无关旧兄弟；待挂接子树与祖先环路检查仍需工作量。 |
| `numChildren`／`getChildAt` | 直接以常数时间读取数量／索引，不复制列表。 |
| 分离最后一个子对象 | 直接检查并移除末尾元素。 |
| 移除任意中间子对象 | 搜索和数组移动仍随兄弟数量线性增长。 |
| 向初始未绑定树追加 | 整树发现／绑定仍可能重扫既有后代。 |

本增量不对树构造、任意重挂接、释放、遍历或渲染作全局 O(N) 保证，也不证明性能领先。

## 第一轮 2D 开销削减

四处改动降低了上面测得的 CPU 开销。它们不改变任何公开接口、帧记录、顶点、uniform 块、逻辑计费、拒绝结果或拒绝顺序。

- **按索引插入。** `addChildAt` 过去每次调用都遍历接收者的整棵树。现在，一个已绑定的接收者，只要有一次插入遍历过它的整棵树并使整棵树绑定到同一个 Engine，就会被记住；此后对它的插入只遍历传入的子树，因为重复遍历会产生的每条记录都有效且带有该 Engine。节点只能通过 `addChild` 或 `addChildAt` 进入被记住的树，两者都会把整棵传入子树绑定到接收者的 Engine；分离或处置节点会把它移出这棵树，而亲和不会改变。私有的 UI 提交和预备子树列表替换，会使包含其目标的每一棵树的记忆作废，所以下一次插入会重新完整遍历该接收者。传入子树和来源直接边仍按[插入契约](容器按索引插入契约.md)的要求在每次调用时捕获并验证；没有 Engine 的接收者仍然每次都遍历。插入仍会把接收者的子节点列表复制两次，因为它在发布前要准备一份完整的替换列表，所以剩余的开销仍随兄弟节点数量增长，只是增长率小得多。
- **帧捕获。** 共享捕获过去遍历两次树：一次接纳所有节点，一次为要绘制的节点生成命令。现在只遍历一次。对可见内容的拒绝会保留到整棵树的其余部分都接纳完成之后，因为任何位置的接纳拒绝都优先于它，所以报告的拒绝不变。材质和区域先按对象、按数值查找，之后才构造文本键；同一条裁剪链下的绘制共用一份冻结的裁剪列表。
- **裁剪后的几何。** 一次绘制的角点只创建一次，并在原处变换到后备空间，而不是每一步都复制。没有改变多边形的步骤直接返回原多边形，而不是副本。谓词、比较以及它们的计费，仍是相同顺序的相同调用。
- **顶点行。** 一帧的顶点行直接写入同一块内存，uniform 块写入另一块；每次绘制的 `data` 和 `uniform` 是各自区间的视图，长度和字节与它们所取代的独立数组相同。

## 跨区域合批

同一页、同一材质上连续的绘制现在合成一批，区域和透明度不同也可以。以前，绘制的区域和透明度放在它自己的 128 字节 uniform block 里，所以每个显示图集另一帧的位图、每个透明度不同的位图，都是一次单独的绘制。现在每个顶点自带区域在表中的位置和所属绘制的透明度，帧内所有区域组成的表只上传一次；两种布局都写在[共享渲染 profile](shared-render-profile-contract.md)中。遇到另一页、另一种材质、另一种绘制、屏障，或者下一个区域落在区域表的另一个窗口（每个窗口 341 个区域）时，一批仍然结束。公开接口、帧记录和拒绝行为都没有变化。顶点从 44 字节增加到 52 字节，帧内每个区域收取 48 字节。

同一工具、同一台机器，先是改动前的代码：

| 负载 | 绘制次数 |
| --- | --- |
| 5,000 个位图，显示同一图集的 100 帧 | 5,000 → 1 |
| 5,000 个位图，显示同一图集的 200 帧 | 5,000 → 1 |
| 5,000 个填充矩形 | 1 → 1 |

对这两个图集负载，形成批次这一步由 0.4 ms 变为 1.0 ms，因为合并后的一批要把各行复制到一个数组里；其余步骤的差别在两次运行的波动范围内。

输出是否不变，用三种方式检查。`tests/shared-frame-golden.test.mjs` 说明捕获的帧、裁剪后的几何，以及每个顶点行的前十一个值与原来相同。`tests/shared-batching.test.mjs` 说明哪些绘制合成一批、新增的值存放什么。此外，用改动前的构建和改动后的构建，通过两种 Host，在使用软件渲染的无头 Chromium 中各画了 46 个场景，并比较读回的字节：92 对全部相同。这些场景是 `tools/shared-rendering/native-cases.json` 中的 26 个二维用例，加上二十个生成的场景：每个有 120 到 1,500 个精灵，取自一到两张图集，包含裁边和旋转的区域、小数透明度、四种采样策略、四种混合、裁剪矩形、实心矩形、网格和九宫格，单帧最多 804 个区域。在单图集、单材质的生成场景中，每帧的 WebGL2 绘制调用从约 390 次降到约 60 次；剩下的来自这些场景中的裁剪矩形，每个裁剪矩形都是一道屏障。这项比较证明的是在一种软件渲染器下像素相同，不是在硬件 GPU 上的运行；`tools/shared-rendering` 中保存的原生证据也没有重新采集。

## 跨页合批

连续的绘制现在可以合成一批，页不同也可以，一批最多八张页。以前页属于一批必须相同的内容，所以轮流使用两张图集的位图各自是一次绘制。现在区域表中每个区域的那一行写明区域所在的页和该页的尺寸，一批的 uniform 块写明八个纹理单元各持哪一张页；两者都在[共享渲染配置](shared-render-profile-contract.md)中说明。只有一张页的一批和以前一样，由带一个页纹理的管线绘制；有多张页的一批由第二条带八个页纹理的管线绘制。一批仍然在遇到另一种材质或另一种绘制、屏障、第九张页，以及下一个区域落在区域表另一个窗口时结束。公开接口、帧记录、顶点、逻辑收费和拒绝条件都没有变化。Host 现在要求设备或上下文提供八个纹理单元。

下面的图形设备工具在无头 Chromium、软件渲染下运行一轮快速测量，先是改动前的代码：

| 负载 | 绘制次数 | submit，WebGPU | submit，WebGL2 |
| --- | --- | --- | --- |
| 轮流使用 8 张图集的 5,000 个位图，全部移动 | 5,001 → 2 | 79.33 → 10.99 毫秒 | 37.52 → 15.32 毫秒 |

软件渲染器自身在这一帧上花费的时间变长了，WebGPU 下从 278 毫秒升到 432 毫秒。它在 CPU 上运行片元阶段，而第二条管线每次读取页时都要在八个纹理中选择。只有一张页的帧由第一条管线绘制，时间没有变化：同一图集的 5,000 个位图，改动前 148 毫秒，改动后 158 毫秒。硬件 GPU 上第二条管线的表现还没有测量。

七个场景，每个有 3 到 20 张尺寸各不相同的页、160 到 600 个精灵、三种采样策略、按页采样的材质和四种混合，用改动前的构建和改动后的构建、通过两个 Host、在同一个软件渲染器中各画一遍。全部 14 对读回的像素相同，此前那次比较的 92 对也相同。在这七个场景中，每帧的 WebGL2 绘制调用从 135 到 570 次降到 2 到 69 次。这证明的是在一种软件渲染器下两个构建的像素相同。它不是在硬件 GPU 上的运行，也没有比较两个 Host 彼此：在这个渲染器中，两个 Host 对生成场景的读回每一百个像素有一到三个不同，出现在两个光栅器插值不同的地方，改动前后都是如此。

## 帧与帧之间保留的记录

以前每一帧都被完整地捕获和准备，不管它和上一帧相比变了多少。现在每个显示节点保留捕获从它派生的记录，每个 Host 保留它上一帧已准备的绘制。[共享渲染配置](shared-render-profile-contract.md#保留的记录)说明保留什么、何时再次使用。使用保留记录生成的帧就是不使用它们生成的帧：每一个值、每一笔收费、每一次拒绝都相同。公开接口没有变化。

开发机上运行 `tools/bench-2d.mjs` 的结果。“保留”指同一帧再来一次；对捕获而言，是没有任何东西移动的一帧，对比全部移动的一帧：

| 负载 | 阶段 | 每帧重新计算 | 保留 |
| --- | --- | --- | --- |
| 5,000 个实心矩形 | 捕获 | 6.93 毫秒 | 3.53 毫秒 |
| | 裁剪后的几何 | 7.71 毫秒 | 0.87 毫秒 |
| | 顶点行 | 4.64 毫秒 | 2.96 毫秒 |
| 20,000 个实心矩形 | 捕获 | 37.75 毫秒 | 22.98 毫秒 |
| | 裁剪后的几何 | 39.98 毫秒 | 3.20 毫秒 |
| | 顶点行 | 15.42 毫秒 | 11.10 毫秒 |
| 显示同一图集 200 帧的 5,000 个位图 | 裁剪后的几何 | 6.98 毫秒 | 1.00 毫秒 |
| | 顶点行 | 3.49 毫秒 | 1.86 毫秒 |

另一次运行中，5,000 个位图画 240 帧，每帧有十分之一在移动，几何用时 1.8 毫秒，对比 6.0 毫秒；顶点行 1.9 毫秒，对比 3.7 毫秒。全部移动时，保留的内容都用不上，保留绘制的 Host 在几何上比不保留的多花约 4%。

当时每一帧仍然要做的事：对每个节点计数、检查和收费，读取每个资源；把每个绘制的顶点行复制到该帧的缓冲区，拼接批次，并全部上传。顶点行和批次后来的变化见[帧与帧之间保留的打包记录和批次](#帧与帧之间保留的打包记录和批次)。

两个测试把每一帧用两种方式各捕获、各准备一次，要求结果相同，包括拒绝，既针对指明的改动，也针对随机改动的场景：共捕获 640 帧，准备 250 多帧。像素比较用的 57 个场景，每个由同一个 Host 连画三次，两个 Host 都做，在无头 Chromium、软件渲染下运行：第一次让一部分节点移动、变淡或隐藏，后两次保持原样。全部 114 次运行的第三帧，与此项改动之前的构建只画一帧的结果逐字节相同。这不是在硬件 GPU 上的运行。

## 帧与帧之间保留的打包记录和批次

Host 保留了绘制的几何和顶点行之后，每一帧仍然要把这些顶点行复制到该帧的缓冲区，为每个绘制写一个 128 字节的块，把每个绘制和它前面的绘制比较一遍，再把所有顶点行复制一次来拼接批次。现在，静止的绘制只打包一次，打包成一条由 Host 保留的记录；批次也只拼接一次：之后只把发生变化的绘制的顶点行写进 Host 为这个批次保留的数组。相邻的绘制如果材质、页和绘制种类都相同，就共用一个块。具体条件见[共享渲染配置](shared-render-profile-contract.md#保留的记录)。帧还是同一帧，每个批次、每一行都相同。公开接口没有变化。

开发机上运行 `tools/bench-2d.mjs` 的结果，取 40 帧的中位数，对比的是此项改动之前和之后都保留记录的 Host：

| 负载 | 阶段 | 之前 | 之后 |
| --- | --- | --- | --- |
| 5,000 个实心矩形，同一帧再来一次 | 顶点行 | 1.56 毫秒 | 0.27 毫秒 |
| | 批次 | 0.82 毫秒 | 0.03 毫秒 |
| 20,000 个实心矩形，同一帧再来一次 | 顶点行 | 9.67 毫秒 | 1.34 毫秒 |
| | 批次 | 3.63 毫秒 | 0.12 毫秒 |
| 显示同一图集 100 帧的 5,000 个位图，同一帧再来一次 | 顶点行 | 1.62 毫秒 | 0.29 毫秒 |
| | 批次 | 0.84 毫秒 | 0.04 毫秒 |
| 同样的位图，每帧有一个在移动 | 几何、顶点行和批次 | 2.83 毫秒 | 0.90 毫秒 |
| 同样的位图，每帧有十分之一在移动 | 几何、顶点行和批次 | 5.62 毫秒 | 3.20 毫秒 |

保留绘制的裁剪几何，用时与之前相同。另一次运行中，同样的位图全部移动，画 300 帧，这时没有任何记录可以再次给出：顶点行的用时少了约五分之一，因为相邻的绘制共用一个块；批次的用时不变。

按配置的逻辑口径，一个保留的位图计 1,136 字节的几何和顶点行、240 字节的打包记录，在保留的批次里再计 328 字节。因此 Host 保留内容的上限从 32 MiB 提高到 48 MiB，按最大限制被接受的一帧，保留的内容仍低于这个上限。

当时每一帧仍然要做的事：对每个节点计数、检查和收费，读取每个资源，在没有任何东西移动的一帧里，这在当时已经占了大部分时间，后来的变化见[静止的节点](#静止的节点)；每个批次的每一行都要上传，不管有没有变化。顶点行数量发生变化的绘制，例如正在穿过屏幕边缘的精灵，它所在的批次在那一帧重新拼接。

把每一帧用两种方式各准备一次的那个测试，现在也用两种方式各打包、各合批一次，要求批次相同、顶点行相同，既针对指明的改动，也针对随机改动的场景，其中一部分只给拼接留很少的额度。分阶段上传的帧在之后的帧准备完成后才读取顶点行，所以它得到的是自己的批次；每个 Host 各有一个测试，在分阶段提交和上传之间画一帧改动过的场景，要求分阶段的帧上传的是它自己那个场景的顶点行。像素比较用的 57 个场景，在无头 Chromium、软件渲染下通过两个 Host 用两种方式各画了一遍。先按原样画两次，再改动，再按原样画两次：全部 114 次运行的最后一帧，与此项改动之前的构建只画一帧的结果逐字节相同。先按原样画三次，再改动：全部 114 次运行里改动后的那一帧，与此项改动之前的构建单独画改动后场景的结果逐字节相同。这不是在硬件 GPU 上的运行。

### 直接提交的 CPU 合批暂存

每个 Host 为拼接绘制批次的 CPU 临时数组提供共享的 8 MiB 预算。WebGPU 在同步队列复制和命令编码完成后归还本帧额度。WebGL2 在同步 `bufferSubData` 调用和绘制完成后归还本帧额度，CPU 顶点、uniform 和区域表视图只在本次提交中使用。待完成记录保留用于准入检查的不可变顶点与 uniform 字节数。较早的 GPU 工作尚未完成时，后续帧可以使用已归还的 CPU 额度。原生资源的所有权与回收仍以原有完成凭据为准。分阶段提交保留各自的 CPU 批次数据，供后续阶段读取。

## 静止的节点

捕获保留了它从每个节点派生的内容，但仍然要把节点的每个值和保留的值比较一遍，在帧内各表里查找它的材质和区域，再把将要生成的命令和上一次生成的命令比较一遍。现在，一个没有被记录过任何改动的节点，如果父节点给它的矩阵、透明度、裁剪和材质都相同，它在帧里的位置也相同，就直接再次给出它的命令，上面这些都不做。它仍然被计数、检查和收费，它的 lease 仍然被读取。具体条件见[共享渲染配置](shared-render-profile-contract.md#保留的记录)。帧还是同一帧。公开接口没有变化。

以前一次捕获还会把访问过的每个节点记在它自己的一个集合里，用来拒绝被遇到两次的节点。现在捕获把自己的编号留在节点上，检查相同，但不再需要这个集合。

开发机上运行 `tools/bench-2d.mjs` 的结果，只看捕获，取每次运行的中位帧，再取三次运行中居中的那一次：

| 负载 | 每帧移动的数量 | 之前 | 之后 |
| --- | --- | --- | --- |
| 5,000 个实心矩形 | 都不动 | 3.19 毫秒 | 0.86 毫秒 |
| | 十分之一 | 3.40 毫秒 | 1.34 毫秒 |
| | 全部 | 5.56 毫秒 | 4.62 毫秒 |
| 20,000 个实心矩形 | 都不动 | 17.37 毫秒 | 5.60 毫秒 |
| | 十分之一 | 21.90 毫秒 | 9.25 毫秒 |
| | 全部 | 27.27 毫秒 | 22.69 毫秒 |
| 显示同一图集 100 帧的 5,000 个位图 | 都不动 | 3.80 毫秒 | 1.51 毫秒 |

在这台机器上，各次运行之间的差别最多可达三分之一，所以表中取居中的一次。静止的位图比静止的矩形花费多，因为要读取它的 lease。

每一帧仍然要做的事：访问每个节点，检查它是这个引擎的存活节点并且在它的父节点之下，对它收费，并读取每个位图的 lease。自带裁剪、边界、效果、Mesh 或文本的节点从不静止；它下面的节点可以静止。整棵没有变化的子树一起跳过，还没有做：那意味着不访问其中的节点，也就不检查它们。

把每一帧用两种方式各捕获一次的那个测试，它的每个用例都覆盖了静止的节点，包括随机用例。新增了两个用例：在静止节点背后销毁纹理或节点，拒绝与不使用保留记录时相同；32,768 个静止的绘制，在它们之前的一个绘制移到八层裁剪之下以后放不进这一帧，拒绝与不使用保留记录时相同。像素比较用的 57 个场景，通过两个 Host 按三种顺序各画了一遍：按原样画两次、改动、再按原样画两次；按原样画三次再改动；先改动再按原样画两次。全部 342 次运行的最后一帧，都与此前各构建的同一帧逐字节相同。这不是在硬件 GPU 上的运行。

## 图形设备上的固定 2D 负载

`node tools/bench-2d-gpu.mjs` 在浏览器中通过共享 WebGPU Host 和共享 WebGL2 Host 绘制七个固定负载，画面为 1280 × 720。`tools/bench-2d.mjs` 测到图形 API 之前为止，这个工具从那里往后测。它会打印一个地址；在要测量的机器上用浏览器打开这个地址，负载就会运行，页面结束后工具打印结果表。加上 `--playwright <已安装的模块>` 时由工具自己打开浏览器：`--channel msedge` 指定一个已安装的浏览器；除非给出 `--headless`，窗口是可见的，因为隐藏的窗口可能不使用显卡。`--quick` 运行较短的一轮，`--json` 打印完整报告，`--backends` 和 `--only` 缩小运行范围。

每个负载先预热资源，再分别记录串行 CPU 提交和独立的 GPU 计时批次。帧节奏阶段在每次浏览器动画回调尝试绘制一帧。仅 GPU 计时批次发出计时查询。结果表包含以下指标。

- **draws** 记录每个串行帧的原生绘制次数，包括最后复制到画布。
- **capture** 记录 Engine 帧捕获。**submit** 记录同步 Host 准备与提交。**settle** 记录提交后等待 Host 完成的时间。
- **gpu** 来自独立一组提交。WebGPU 累加已插入时间戳的渲染通道。WebGL2 需要非零位数的计时计数器，记录第一次绘制至调用完成围栏前的区间。发生 disjoint 时整批失效。计时不可用、失效或不受支持时，时长留空。
- **interval** 和 **p95** 记录负载下的浏览器动画回调间隔。**refused** 记录该阶段的 Host 背压拒绝。实际屏幕呈现需要独立测量。请保持页面在前台。

GPU 探针复用已预热的 Host 和资源，收完查询后在帧节奏阶段关闭计时。Engine 和 Host 实现保持原样。计时受浏览器时间戳精度与两种后端不同区间的约束。 [WebGL2 计时扩展](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/) · [WebGPU 时间戳精度](https://www.w3.org/TR/webgpu/#timing-attacks)

下方原始软件渲染实验使用较早的计时路径，保留其绘制计数和 Host 测量作为历史证据。

在无头 Chromium、软件渲染、两个共享核心上运行的一轮快速测量完成了全部十四行。其中的设备时间描述的是软件渲染器，不予保留；绘制次数和 Host 的 CPU 时间是 WebGPU 工作的起点：

| 负载 | 绘制次数 | submit，WebGPU | submit，WebGL2 |
| --- | --- | --- | --- |
| 同一图集的 5,000 个位图，全部移动 | 2 | 24.03 毫秒 | 17.35 毫秒 |
| 同一图集的 5,000 个位图，全部静止 | 2 | 11.19 毫秒 | 16.98 毫秒 |
| 轮流使用 8 张图集的 5,000 个位图，全部移动 | 5,001 | 79.33 毫秒 | 37.52 毫秒 |
| 同一图集的 20,000 个位图，全部移动 | 2 | 77.01 毫秒 | 60.39 毫秒 |
