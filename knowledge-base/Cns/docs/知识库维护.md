# 知识库维护

[English](../../en/docs/knowledge-base-maintenance.md) | 简体中文

知识库与引擎共同维护。产品文档解释目标与设计理由，契约定义行为，登记册维护决策与交付，验证记录说明可复现的观察。[阅读索引](../README.md)和[当前版本](../当前版本.json)提供统一入口。

## 更新顺序

1. 登记来源、日期、版本和证据范围，区分观察与假设。
2. 用稳定编号关联受影响的需求、决策、实现和验收记录。
3. 同步更新中英文解释文档，说明设计变化的理由，正文围绕当前连贯的产品方案组织。
4. 刷新当前文档身份和英文登记册视图，检查链接与共用状态，再审阅技术含义和翻译。

在知识库根目录运行结构检查：

    pwsh -NoProfile -File tools/Validate-KnowledgeBase.ps1 -CheckOnly

知识库文档的相对链接保持在 `knowledge-base` 目录内；仓库根目录的规范、贡献指南和鸣谢使用对应的 GitHub 规范 URL 引用。

## 职责与维护节奏

维护者审阅范围与集成，领域审阅者核对契约和证据，贡献者保证来源与示例可复现。角色分工通过社区治理公开。证据、设计或交付变化时同步更新，并定期检查失效来源和未解决工作。

## 维护开源参考

记录查阅的版本或提交、相关机制、许可证及实际用途。研究参考、产品依赖和集成实验分别管理。引用紧邻其支持的结论，署名汇总于[鸣谢](https://github.com/cnedwin/Egret_rebuild/blob/main/ACKNOWLEDGEMENTS.zh-CN.md)。参考实现帮助技术分析，白鹭自身的契约与测试定义产品行为。

## 维护实现来源

遵循[实现与依赖规范](独立实现与第三方依赖规范.md)，在[来源记录](../templates/实现来源记录.md)中说明使用材料、第一方范围、依赖、AI 辅助和审阅，并登记升级及受影响的验证。

## 公开阅读与历史证据

设计文档使用中性的项目表述，说明问题、约束、备选方案与选择理由，不复述对话或答复角色。重要技术变化进入决策或带日期的验证记录，日常文字修订留在版本历史中，不把未记录的个人想法或结论归于任何人。

阅读文档可随产品成熟重新组织，同时保留来源鸣谢、数值结果、不确定项、原始证据和既有审阅范围。历史哈希继续标识历史文件，当前文字登记自身身份。两种语言同步维护，共用同一套产品计划。
