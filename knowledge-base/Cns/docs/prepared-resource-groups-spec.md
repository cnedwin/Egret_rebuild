# 资源组准备与 Bitmap 整组发布

[English](../../en/docs/prepared-resource-groups-spec.md)

本契约规定如何准备一组 Texture 资源，再将它们一起发布到现有 Bitmap。资源加载、绑定发布和 Host 呈现是三个独立操作。本能力不新增渲染器，也不改变 AssetGroup 成员的所有权。

## 目的

角色或界面可以包含多个相互配合的图片层。一个层准备完成时，其他层可能仍在加载，此时不应提前替换部分画面。替换还需要保留显示对象、变换和输入身份。应用先通过 AssetGroup 准备完整且兼容的资源，再通过 Bitmap 绑定票据显式发布。

典型场景包括需要整组切换的服装层、多部件角色立绘和相关联的界面图片。候选加载期间，当前已发布集合继续可用。若候选加载、内容校验、预算接纳或票据准备在提交前失败，只退休候选并保留旧集合，前提是旧集合的所有者仍然有效。

循环调用普通 Bitmap setter 无法提供这一契约：后序目标可能在前序目标已经改变后拒绝写入。票据在任何绑定发布前检查全部目标。它还识别期间发生的重复赋值；即使公开 lease 和裁剪区域与原值相同，原始绑定身份也已经改变。

## 阶段与完成 Promise

准备过程包含不同阶段：源数据读取与校验、解码为 Texture 资源、AssetGroup 就绪、绑定发布，以及 Host 呈现。AssetGroup 可以已经 `ready`，但其成员仍未发布。其稳定的原始 `ready` Promise 只表示就绪，不表示票据提交、呈现或资源退休。票据的 `prepare`、`commit` 和 `dispose` 不引入 Promise。

示例协调器返回为每次替换请求创建的原始 Promise。只有该请求提交且业务选择更新后，Promise 才成功兑现。失败、取消或被新请求取代的请求以拒绝结束，不发布部分替换。应持有并观察原始结果，不能用清理或呈现 Promise 替代。请求提交成功后，后续退休即使报告失败，也不改变已提交请求的成功结果；报告失败时需要区分发布与清理。

在场景组合中，会话就绪表示 CPU 侧所有者构建及依赖策略检查完成。仅凭会话就绪成功，不能证明原生字体注册、渲染像素、GPU 完成或外部适配器关闭已经通过验证。

示例本地的 `createPreparedResourceApplication` 通过只读 `input` 访问器返回已持有的真实 MouseInput；它不是 SDK 导出。启动期间，访问器可以返回 `undefined`。等待原始 `app.ready` 后，使用者可通过 `session.scene.engine.stage.on` 订阅 `app.input.events.activate`，并使用 `session.scene.inputScope.signal` 管理订阅生命周期。访问器不创建第二个输入所有者或新的 EventType。输入销毁仍由应用关闭负责。

## 公开接口

```ts
import type { AssetLease, Bitmap, Scope, Texture } from '@egret/engine';

// Selected Engine method:
interface Engine {
  captureBitmapBindings(scope: Scope, targets: readonly Bitmap[]): BitmapBindingTicket;
}

interface BitmapBindingTicket {
  prepare(members: readonly AssetLease<Texture>[]): void;
  commit(): void;
  dispose(): void;
}
```

`BitmapBindingTicket` 是编译后擦除的 TypeScript 类型。根入口不提供票据构造器、独立工厂，也不额外导出独立的运行时批量函数。返回的句柄被冻结，三个方法要求以原句柄作为接收者。prepare 和 commit 均为同步操作，返回 `void`。

捕获接受同一 Engine 中 1–128 个互不重复、存活且具有非空绑定的 Bitmap，以及该 Engine 中处于打开状态的 Scope。目标和成员必须是稠密数组，每个索引位置必须是数组自身属性。成员数必须与目标数相同。允许重复使用同一个真实成员 lease，拒绝重复目标。

应用需要独占管理这些普通 Bitmap 的绑定。不要让同一绑定同时交给 Bitmap resource slot、Button 皮肤或序列动画裁剪所有者管理。场景组合为序列动画身体层单独持有图集 lease 和动画 Scope。票据只发布普通的外衣与装饰 Bitmap 层。替换这些层不会重定向身体图集，也不转移动画裁剪的所有权。工厂不会自动识别所有应用层所有者。

## 准备与提交

捕获保存目标当时的精确绑定身份。`prepare` 快照有序成员并验证有效 Texture view，不改变目标。提交时使用候选的完整 Texture view，包括非零起点和自然尺寸。内容版本、布局兼容性及应用资源预算应在 `commit` 前检查。

提交重新检查整组：目标归属与生命周期、正在进行的目标修改、全部捕获绑定身份、旧绑定和候选成员的有效访问权。全部绑定身份检查先于任何访问权读取。实现先准备好发布记录，再开始统一写入，期间不调用应用代码。普通拒绝不会留下部分发布。

票据保留每个 Bitmap 的身份、父节点、顺序、变换、锚点、可见性、hit area 和事件订阅。绑定成功不代表帧已完成、GPU 已提交或画面已经显示。应用需要另行捕获和呈现帧，并等待 Host 对应的完成屏障。

## 重试与退休

| 操作或条件 | 结果 |
|---|---|
| 首次成功准备前，准备输入或访问权无效 | 不写目标；修正后可以再次准备。 |
| 成功准备后再次调用 prepare | 拒绝；不能替换已准备的集合。 |
| 提交时遇到暂时的目标修改或访问权拒绝 | 不写目标；原绑定和所有者仍有效时，准备结果可继续使用。 |
| 期间发生目标赋值，包括同 lease 或完整 view 重复赋值 | 票据因绑定冲突而终止；新的尝试需要重新捕获。 |
| 捕获目标被销毁 | 票据终止，不恢复其他目标。 |
| 提交成功 | 准备结果只消费一次。 |
| 提交前 dispose | 初始绑定保持不变。 |
| 提交后 dispose | 只清理仍具有本票据精确发布身份的绑定；后续手工或新票据的绑定保持不变。 |

`dispose` 幂等，不恢复初始资源，也不释放成员 lease。外部释放 group-owned lease 或销毁其 Texture 会使借用失效，票据不能撤销这一操作。后续手工绑定如需独立存续，应使用独立持有的 lease。先改走绑定、再改回同一 lease 和 view，仍构成 ABA 冲突：公开值相等并不恢复捕获身份。发生这种变化后，需要新建票据。旧票据清理不得清除后续手工绑定或新票据的发布。

方法在读取新输入前，依次检查真实接收者、Engine 内在生命周期、捕获的 Scope 生命周期和终止原因。输入 getter 不能复活已销毁的票据或已关闭的所有者。准备期间重入同一票据会被拒绝。普通 Engine 帧捕获不会整体禁止使用其他条件有效的票据。

Engine 关闭时，先让全部票据终止并条件清理全部已发布绑定，再释放资源组及其他可能调用外部代码的所有者。普通 Scope 保持先 abort、再反向清理的既有行为；Scope 一旦关闭，内在生命周期检查立即拒绝新的准备或提交。

## 资源所有权与应用协调

AssetManager 负责获取、缓存和 provider 销毁。Scope 安排生命周期清理，不是另一份资源缓存。AssetGroup 仍是成员 lease 的唯一清理所有者。票据只借用 ready 返回的精确成员，不重新获取、不收养、不认领、不转移，也不释放。应用应先退休发布，再退休 group。每次尝试使用短期 binding Scope 和 group Scope，在长期 scene Scope 中只登记一个应用协调器清理入口。

实现最新请求生效时，协调器需要先公布新的意图身份，再取消旧准备或激活加载器。清理或加载器重入后重新检查该身份。只有最新且有效的尝试可以检查完整清单和预算、准备票据并提交。提交成功后，先更新业务选择并兑现成功，再退休旧资源组；清理重入不能覆盖更新的选择，也不能把已成功发布改报为未提交。

逻辑取消与源任务真正完成不同。取消待完成的替换会撤销其发布权限并启动所有者清理，但不能证明读取器、解码器或其他原始源任务已经停止。过期任务的完成结果仍需被观察并退休，不能改变当前选择。原始加载任务直到实际结束，才归还源任务预算。逻辑工作集、编码源数据保留、CPU 解码数据、帧工作量、GPU 常驻资源和临时分配应分别记账。提交后的帧拒绝不能证明提交前已经完成资源预算接纳。

## 清理与适配器边界

单次替换先撤销发布权限，再销毁票据、销毁 group Scope，最后完成 binding Scope 清理。可能调用外部代码的清理返回前，继续保留逻辑预算预留。场景关闭先让角色代次和协调器失效，再停止动画、分离并退休显示对象、释放资源组和图集所有者。遇到次要失败时仍需继续清理，并保留主要原因。

会话借用源数据与共享依赖适配器。其稳定的原始关闭 Promise 覆盖自身 Engine、文本缓存清理，以及它观察到并跟踪的源任务和依赖任务。外层应用仍负责关闭借用的适配器，并等待各自原始关闭结果。在 abort 或 disposer 回调可能重入前，先登记终止状态和每个关闭 Promise。重复关闭调用共享同一结果。这些所有权边界不能仅靠源码检查证明原生关闭正确性。

固定服装源适配器校验编码数据身份和完整 Texture view，并把每个已接纳的原始 provider 任务保留在源任务账本中，直到该任务结束。快照只描述其逻辑持有的分配，不包括读取器保留的字节、浏览器内部解码存储、GPU 分配和物理内存回收。协调器限定的集合与字节上限属于示例策略，不是通用 SDK 上限或实测设备容量。

## 错误边界

票据接纳使用 `BITMAP_BINDING_INVALID`、`BITMAP_BINDING_SCOPE_INVALID`、`BITMAP_BINDING_TARGETS_INVALID`、`BITMAP_BINDING_MEMBERS_INVALID`、`BITMAP_BINDING_STATE_INVALID`、`BITMAP_BINDING_REENTRANT` 和 `BITMAP_BINDING_DISPOSED`。真实运行时错误保留既有代码，包括绑定冲突、对象已销毁、Bitmap 正在修改，以及 lease 或 Texture 访问权已撤销。Scope 或 Engine 生命周期错误优先于调用方输入 getter 抛出的错误。

本契约定义有限的 Texture 绑定能力，不代表完整 UI、动画图集重定向、Spine、任意异质资源事务、GPU 回滚、物理取消、设备恢复或目标设备性能已经完成。实现、公开行为、权限单元、类型、原生呈现和最终交付分别记录证据。

## 验证与交付状态

规格、保存的 CPU 结果、真实原生呈现和交付属于不同证据类别。源码审查核对公开接口与所有权设计。CPU 控制可以覆盖请求次序、失败、重入和逻辑清理，但不能证明实际 PNG 解码、原生字体就绪、输入行为、Canvas/WebGPU 像素、GPU 预算或物理资源退休。

有限桌面组合、原生输入和已记录的所有者退役结果见[验证记录](prepared-resource-groups-evidence.md)。通用原生支持、物理／GPU 预算及目标设备结果仍保持开放；仓库完整门禁与 Git 交付具有各自截止点。相关基础能力的既有原生结果不会自动覆盖本场景。中断且没有完成回执的完整检查不能记为通过。测试数量和单独策略检查成功，不代表产品完成或发布验收通过。
