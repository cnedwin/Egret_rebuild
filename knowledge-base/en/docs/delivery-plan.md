Egret has two delivery levels: a usable, honestly scoped engine core, then the complete game-creation and publication product. M0–M4 organize the current core program; V001–V008/V020 retain the larger product obligations. Completing a core milestone cannot silently close the creator platform, general 3D, native hosts or one-click migration.

## Dependency and scope decisions

Project identities, migration differences, asset provenance and target capabilities participate in core interfaces early. This does not require building the complete editor, nine proposed packages or a native VM before a usable Web core.

After the core interface foundations, the larger product proceeds through asset-to-scene 3D, selected host/publication loops, a shared creator/Agent workbench and complete migration. Rights inventory, legacy baselines and interface design may run alongside unfinished external M4 qualification. New implementation is selected as a complete outcome, rather than triggered automatically by a documentation merge.

The all-in-one platform includes coding/debugging, main canvas, UI/animation, 3D scene/effect, world and character tools plus target publishing. User-selected model APIs, Skills, MCP, plugins and visible/configurable token spending belong to its harness. They stay outside Runtime frame authority.

## Evidence and release decisions

A delivery records the requirement, source/artifact/version, environment, expected behavior, actual result and unresolved limitation. Code, controlled tests, actual browser/device observations, performance and real deployment are distinct evidence domains.

An ordinary feature merge requires the existing complete protected checks, independent review, sources, English/Chinese readings and applicable real-browser evidence. It does not require rerunning unrelated historical or milestone campaigns. Sustained lifecycle/performance and real-host claims run when their declared prerequisites and actual artifacts are ready.

For a core preview, publish exact usable entries, examples, dependencies and open rows. A distribution must work in a clean consumer; a source archive or changed private/version field does not prove package acceptance. A public example site requires its own deployment verification.

Complete M4 retains X-D60/1, X-MTouch/1 and the L campaign; unavailable required rows remain open. Full product release additionally requires its declared 3D, creator/publication and migration scope. No missing IME, iPhone, licensed reference, performance or external-service result is converted to success by reorganizing the plan.
