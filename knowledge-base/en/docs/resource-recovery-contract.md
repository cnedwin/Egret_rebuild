M1.5 connects deterministic resource manifests, dependency loading, staged replacement and device reconstruction to one genuine Engine scene. The selected design extends the existing AssetManager, leases, Scope, capture registry and shared Hosts. CPU scene state remains authoritative; native resources belong to one Host and one device generation.

This document specifies the selected behavior and fixed acceptance requirements. At the 2026-10-20 verification cutoff, the [verification record](resource-recovery-evidence.md) reports independently reviewed C7 completion for all seven cases on Windows / Chrome for Testing 157.0.8103.6; C01/C02 each completed 100 resource cycles, ten native losses and 30 minutes in the foreground. All twenty-four affected browser suites completed thirty-six actual calls and independent result review. Final package review and complete protected CI remained required; formal M1.2 performance and external platform/device qualification remain open. Delivery is recorded in the actual PR history. C1–C6 retain their historical outcomes and the old Edge version remains unqualified. Source implementation, controlled checks, actual browser results, formal performance and protected delivery require separate evidence. The [M1 plan](m1-rendering-resource-plan.md), [shared rendering contract](shared-render-profile-contract.md) and [WebGL2 contract](webgl2-executor-contract.md) retain their compatibility boundaries. These are connected steps of one M1.5 package.

## Identity and byte integrity

Versioned project resource entities identify resources by stable logical ID, source/artifact file records, exact importer and tool versions, canonical settings, artifact format, target profile, ordered dependencies and build-affecting provenance. Explicit project references must agree with those records. Duplicate IDs, missing or cyclic dependencies, unsupported versions and invalid paths refuse before provider work.

A single contracts admission authority validates and copies manifest metadata, recomputes topological SHA-256 build keys and rejects claimed-key mismatch. Build keys include source digest/length and dependency IDs/keys; output artifacts are excluded to avoid self-reference. Runtime resource identity additionally includes project/logical ID, verified metadata build key, artifact digest/length, format/media type and target. Equal logical IDs or build keys cannot merge different artifacts. Genuine asset type identity also remains part of acquisition; equal type names do not alias types. URLs locate bytes and do not establish identity.

Metadata admission proves consistency of declarations. The build tool separately verifies actual source and artifact bytes using native crypto; the browser verifies received artifact digest and length before decoding. Parsing a manifest alone proves neither file integrity nor successful loading. Canonical manifest bytes have an external digest receipt, avoiding a self-hashed field.

The selected optional entries are `@egret/contracts/resources`, `@egret/project/resources`, `@egret/engine/resources` and `@egret/engine/web/resources`. Engine/runtime depend on contracts, never project; default package entries remain separate. Admission limits are 4 MiB manifest UTF-8, 4,096 resources, 8,192 dependency edges, depth 32 and 64 KiB settings per entry.

## Groups, dependencies and cancellation

A manifest group admits its complete dependency closure before acquisition and requires one genuine correctly typed binding per selected entry, within the existing 128-member group limit. Dependencies acquire before dependants. The existing manager may coalesce loads, while each group owns independent genuine leases. Group access borrows those leases; callers do not release them. Providers load their own artifacts; application assembly consumes dependency values only after the group is ready and while it remains alive.

The bounded scheduler owns ordering, never values or disposal. Interactive/background FIFO classes admit four interactive acquisitions then one background acquisition while both are waiting, subject to dependency order and coalescing. At most four acquisitions are active and 128 manifest acquisition records are queued per Engine. Closing one group cannot revoke another group's demand.

Each shared browser source permits at most four actual network operations, two actual decoders, 128 waiting operations and 132 retained or quarantined job records. Network waiting, decode waiting and retry delay share the waiting bound across direct readers and every provider. Each encoded input is at most 8 MiB. Before allocating a body, the source reserves twice its expected length within a 32 MiB source budget, covering the stable output and current chunk or native digest input. This conservative reservation remains until actual settlement. The existing PNG provider separately retains its four total jobs, 8 MiB input limit and 32 MiB copied encoded-input budget; these logical ledgers are not a combined physical-memory measurement.

The whole-job deadline starts before caller-context reads and includes queues, fetch, verification, decode and materialization: 10 s by default, at most 30 s. Retry defaults to zero; an explicit option allows one transient network retry after actual transport cleanup and a 100 ms delay inside the original deadline. Integrity, schema and decode failures do not retry.

Cancellation revokes publication before releasing group leases. A rejected waiter, timeout or abort request does not free a running fetch/body-read/decode slot. The captured underlying operation owns that slot until actual settlement; late settlement releases it once. Cancelled queued work can be removed before starting, while its original asynchronous continuations still complete before its retained record is retired. A public refusal alone does not promise immediate replacement capacity. Uncertain operations remain charged and constrain subsequent admission. Source close and provider close each wait for their own actual work, retain incomplete-cleanup outcomes and never close the other owner or dispose manager-owned values.

When a response body has been acquired, cancellation starts its original body or reader cancellation before aborting the fetch. This ordering prevents the fetch abort from first putting a readable stream into an error state. Close still waits for the original cancellation result and reader lock release. A rejected cancellation remains an incomplete cleanup outcome with its original cause and retained resource charges.

## Stable Host and generation recovery

One shared Host facade owns replaceable native sessions. Session state distinguishes new, starting, ready, stopped, lost, restoring, failed, closing and closed; generation tokens authorize asynchronous publication. Concurrent readiness/recovery callers share the applicable stored barrier. Readiness requires native qualification, pipelines/targets and accounted old-generation retirement. Historical first failure remains recorded after successful recovery; current-generation failure clears only on success.

Shared WebGPU recovery is opt-in. Omission preserves existing terminal loss behavior. Automatic recovery applies only to acquire-owned devices. Manual acquire-owned recovery reacquires a native device; borrowed recovery requires an explicitly supplied fresh genuine device. The Host never destroys borrowed devices. Old/textured/B1 entries preserve their existing failure, stopped/start, error and close semantics. No restart-from-stopped capability is added.

Loss revokes the generation before reentrant publication. Stale acquisition, validation, upload, completion and readback can settle their own owners but cannot publish into a later generation. Close revokes recovery before cleanup, settles late owned devices and detaches late borrowed devices without reopening. Recovery preserves Engine, Stage, Scope, leases, scene/animation state and game clock; the application explicitly selects and replays its immutable frame.

Confirmed native loss can invalidate still-known native owners of that exact generation. CPU work and callbacks must still settle. For staged submissions and opt-in recovery, every owner already classified unknown remains permanently charged and unsafe, even after actual loss of the same device. A fresh generation cannot erase unknown cleanup; unreconciled unsafe ownership makes recovery terminal. Product recovery deadlines remain 10 s default/30 s maximum, separate from stricter acceptance targets.

WebGPU immediate submissions with recovery omitted retain their existing terminal accounting: after original operations settle and cleanup is attempted once, logical pending counts may retire while unsafe close and surface quarantine remain. A zero pending count does not establish successful native destruction. This compatibility rule grants no recovery or safe reuse of unknown ownership. For new stages, a rejected error-scope observation retains the original charge; a fulfilled validation error can release it after the remaining proofs and cleanup succeed. The original failure remains the reported cause.

Idle waits snapshot accepted work and call-time state. A snapshot containing work affected by loss rejects after its cleanup; an empty healthy snapshot is not retroactively invalidated. A later healthy-generation snapshot can succeed despite historical failure under opt-in semantics.

The optional shared Host methods are `getSessionStatus()`, `whenReady()` and `stageSharedFrame(frame, options?)`; scene Hosts additionally expose `stageSceneSharedFrame(scene, overlay, options?)`. Only shared WebGPU exposes `recover(device?)`. Session status is frozen and reports state, generation, attempt, historical first failure and current-generation failure. Existing WebGPU status projects ready as active, lost as failed and restoring as starting; its original state union remains unchanged. Only shared WebGPU readback adds generation metadata. The six common session/upload types are erased exports of the optional backend entries.

Each WebGPU loss episode permits at most three actual recovery attempts, including its one automatic attempt. A safely settled failure requires a later explicit retry; there is no automatic retry loop. Initial startup is attempt zero. Failed caller-device validation changes neither the attempt count nor readiness barrier. A successfully captured fresh native generation advances its token even if reconstruction subsequently fails; the episode allowance resets only after actual readiness followed by a later genuine loss. Exhaustion, deadline expiry or uncertain cleanup is terminal. A public timeout never establishes that acquisition or native work has ended.

Every opt-in initial and replacement device, owned or borrowed, must pass the actual browser GPUDevice lost/limits getters and fixed method capture. Only fulfillment of that captured native lost promise establishes invalidation for its exact generation. A rejected observer or a structural device with a lost promise does not. Already unknown ownership remains unknown. Recovery-omitted admission keeps its established compatibility behavior.

During lost/restoring, `start()` refuses without acquisition; `whenReady()` observes the current barrier. A safely failed attempt leaves that barrier rejected until a valid explicit retry publishes the next one. Stopping revokes pending recovery and unsubmitted upload publication before cleanup callbacks, enters stopped, and prevents later acquisition, reconstruction or reopening. Already-started work remains owned through settlement. The original initial-start promise and submitted work preserve their established settlement timing. WebGL2 retains its existing restoration policy and has no WebGPU recovery-attempt limit.

## Candidate capture, staging and commit

`Engine.capturePreparedSharedFrame(ticket, options)` synchronously captures a genuine prepared binding ticket belonging to the same Engine and a live Scope. It returns an immutable `SharedRenderFrame2D` through the existing shared traversal and completion registry. Frame IDs, capture budgets and frame/clock reentry rules remain shared with ordinary capture. Capture neither invokes the Host nor advances the clock, consumes the prepared ticket or takes ownership of group leases.

One private view selects the complete candidate Bitmap state: source, crop, view region, logical/natural dimensions, trim and rotation metadata. All-tree admission and visible geometry use that same view; attached visible content retains the current authored transforms, ancestor clips and order. Every selected target, including hidden or detached targets, undergoes binding-state and old/new lease-authority validation before and after traversal. Capture makes no live binding, bounds-cache or revision writes, and subsequent ordinary, legacy and textured captures continue to use the old binding until commit.

The traversal does not call `getBounds()` or derive authored clips from bounds. Public bounds queries continue to measure the live scene. If a capture path needs an internal bounds measurement, it must use the same candidate view and invocation-local results rather than publish candidate measurements to live caches. The transformed/clipped 16 × 16 to 64 × 64 witness compares candidate frame content with an independently committed reference; live ancestor bounds must remain at their old values until commit. Authored neighbor positions and clips remain authored; capture adds no automatic layout.

Ticket authenticity and prepared phase are checked before caller options. After ordered option reading completes or throws, candidate capture rechecks Engine/Scope/ticket lifetime and phase before selecting an option error. If that recheck succeeds, an option-read failure retains its exact cause, including `undefined`. Target, binding and lease validation begins only after valid options. Refusal spends no frame ID; binding conflicts and lifetime or lease-authority changes retain their existing refusal behavior.

A saved candidate frame retains immutable snapshot semantics during later unrelated visual/tree edits. The ticket still requires current target binding state and old/new lease authority at commit; snapshot capture does not create a whole-scene transaction. Existing `BitmapBindingTicket.commit(): void` remains the separate synchronous publication step. CPU snapshot capture and controlled capture checks establish neither Host stage readiness, native upload/draw completion nor reference-correct browser readback.

Staging reserves full existing charges and one of the same two pending-frame slots used by ordinary rendering. Upload chunks are at most 4 MiB per scheduled task and retain valid row/element alignment. No second staging allowance or full-image concatenation is introduced. Resources stay pinned through readiness until submit/dispose/loss settlement.

Stage readiness establishes native upload/validation completion for its generation. CPU commit, draw submission, native completion and reference-correct readback are separate events. Submission is single-use and transfers the same owner without reupload; stale tickets refuse. A fixed 10 s admission-to-submit deadline includes ready-held time. Idle snapshots include admitted unsubmitted stages until transfer or settled refusal.

When readback is enabled, stage admission reserves the complete possible readback envelope before a request exists. A request is selected only at submit; an earlier ordinary render may bind its own eligible request. GPU accounting includes padded rows and final output; GL includes its pixel-pack storage and output. Scene stages use the final scene-plus-overlay dimensions. Staging cannot resize or reconfigure the visible canvas, acquire its current texture, draw, resolve or read back. It prepares offscreen resources while preserving the previous healthy presentation; actual device loss can invalidate that image.

The upload handle exposes a readonly `ready` promise, `submit()` and `dispose()`. Submit/dispose require the exact returned receiver; detached calls and copied handles refuse before touching Host state. Submit returns frozen generation/frameId/serial metadata and a native `completed` promise. Pixel readback and final resource retirement retain separate observations. A later readback failure cannot revise an already fulfilled native-completion promise. Disposal after accepted submit does not cancel transferred work.

Stage options accept the existing cancellation signal. The signal and listener methods are captured once; aborted is checked before admission and immediately after subscription. Reason is read only after the first observed abort, once, with reentry latched before that read. A synchronous subscription abort, terminal callback or exception unwinds its unstarted charged record and returns no handle. After the handle is returned, cancellation revokes publication while original uploads and proofs remain charged until settlement. Host terminal state takes precedence over an option-read exception; otherwise its exact cause is preserved, including undefined. Listener removal is once-only and does not grant additional capacity.

Application order is: acquire candidate group → prepare binding ticket → capture candidate frame → stage and await ready → synchronously commit CPU bindings and submit without an intervening await → observe completion and independent readback → release old group. Existing `BitmapBindingTicket.commit(): void` remains synchronous CPU binding. Precommit failure preserves old bindings. Postcommit native failure requires explicit fallback or reconstruction/replay; both groups remain owned until that choice settles.

Reload uses the same Engine/manager: retain old leases, admit the replacement closure, invalidate every selected root/dependency ref exactly once before new acquisition, then require fresh CPU resource generations, new image identities and actual shaped fetch/decode. Old leases remain valid for their owners. Reacquiring a READY entry or replaying retained bytes cannot satisfy reload acceptance.

## Run the integrated recovery collector

The opt-in `resource-recovery` suite exercises the M1.5 scene and resource lifecycle through the built public SDK. Complete the normal build and source review first, then use a fresh output directory outside the repository:

~~~text
node tools/browser-verify.mjs --suite resource-recovery --playwright <absolute-installed-playwright-package> --output <absolute-fresh-directory-outside-repository>
~~~

The fixed seven-case schedule covers WebGL2 and owned WebGPU sustained recovery, borrowed-device WebGPU recovery, and four close-during-loss/recovery cases. Each primary backend remains in the foreground for 30 minutes with trusted pointer interactions. Reserve the machine for this run: avoid concurrent builds, source changes, benchmark runs or browser focus changes. The wrapper permits 82 minutes for this suite; the collector has its own earlier work and cleanup deadlines. A deadline is a limit, not an expected execution time or a successful result.

The collector serves only the reviewed local module/asset graph, uses first-party PNG fixtures and records the offline manifest-builder provenance. It shapes actual traffic to 10 Mbit/s and 80 ms, retains raw readbacks/presentation screenshots and rechecks original-owner cleanup. Browser artifacts remain in the external output directory. Inspect both the wrapper `result.json` and `artifacts/report.json`, along with the indexed raw files. All seven cases, source stability, numerical references, resource accounting and cleanup must pass; an unavailable route or incomplete row keeps acceptance open. The synthetic completion tests check receipt validation only. They do not replace this browser run or the separate M1.2 performance acceptance.

### Isolated browser selection

The existing wrapper uses the installed `msedge` channel. The direct collector also accepts an isolated Chromium-compatible executable through `--executable`, mutually exclusive with `--channel msedge`:

~~~text
node tools/verify-resource-recovery.mjs --playwright <absolute-installed-playwright-package> --executable <absolute-browser-executable> --output <absolute-fresh-directory-outside-repository>
~~~

Use the existing pinned Node and Playwright versions on Windows x64. The collector does not install or update a browser, accepts no extra launch flags, and rejects unknown, duplicate, mixed, or relative browser selections. It records the selected executable's canonical path, raw byte length and SHA-256, checks that identity before launch and after cleanup, and retains the actual launched browser version and available CDP version information. An identity change leaves the run incomplete. This fingerprint covers the selected executable, not every file in its browser distribution.

The direct collector writes `report.json` and the indexed raw artifacts directly into its output directory; it does not create the outer wrapper's `result.json`. Its original work and cleanup deadlines remain active. The seven cases, 100 cycles per primary backend, ten actual loss cycles, 30-minute foreground duration, network assertions, reference pixels and cleanup requirements remain unchanged. Report any result for the actual browser version, operating system and device tested. Choosing a different executable or finding an upstream browser fix does not establish a new pass or clear an earlier failure; untested browser versions remain unverified.

## Read-only resource diagnostics

Source, fixed PNG provider and shared-renderer diagnostics are implemented for M1.5 pressure verification. They expose the existing owners' logical accounting through optional browser and shared-renderer entries. They add no allocation authority, scheduler, resource owner or reset operation. The fixed C7 run supplies actual pressure and recovery evidence in the verification record; formal timing and complete package qualification remain OPEN.

ManifestByteSource.getStatus() returns ManifestByteSourceStatus. The fixed manifest PNG assembly returns a ManifestTextureProvider subtype with getStatus(): ManifestTextureProviderStatus; ordinary BrowserTextureProvider keeps its existing surface. Both shared backends and their scene variants expose resources: SharedHostResourceStatus through getSharedStatus(). Existing getStatus() fields and the existing WebGL2 retention projection keep their meanings. Source/provider status methods require the genuine receiver.

Snapshots are fresh, deeply frozen plain data. Each has current, highWater and Boolean saturated; Host snapshots additionally have totals. Counter buckets contain safe nonnegative integers and no native objects, resource identities, promises or timestamps. Reading a snapshot performs no native calls, pumping, eviction, callbacks or cleanup, and remains supported after close. High-water values are updated at actual ownership transitions, including synchronous allocations, rather than only on reads. Each field is its own lifetime maximum; maxima from different fields or generations must not be added as a simultaneous memory peak. Saturated totals cannot support exact quantitative acceptance.

For the fixed PNG provider, blobLogicalBytes is the validated single-part payload length after successful native Blob construction; no additional Blob.size getter is required. activeDecodes covers entry into the captured decoder invocation through settlement of its original result, including the synchronous call interval. A synchronous throw can therefore produce a transient high-water count before the existing finally releases it. unknownNativeObjects counts existing malformed or failed-qualification obligations and objects whose cleanup cannot be established; healthy acquisition before normal validation does not itself create an unknown obligation. Late canceled bitmaps receive no extra dimension reads, and unsuccessful cleanup counts each original object once.

Original settlement and ownership rules remain authoritative. Publication cancellation does not refund an outstanding operation. Clean readBytes transfer removes the source-owned buffer count; clean texture publication transfers the image to its application owner. Quarantined existing references remain reported without creating extra copies or retaining new references for diagnostics. Across device generations, use only the existing bounded owners and scalar history. Known invalidation cannot erase unknown obligations. Legacy immediate GPU pending records may retire while unresolved native cleanup remains visible in unknownNative.

For the selected pressure scene, application accounting deduplicates genuine image identities across groups, leases and retained frames, with geometry and caller-held readbacks recorded separately. Source/provider and Host current snapshots are sampled in one callback-free task; individual lifetime high-water fields report shorter local peaks separately. The 40-page eviction/reupload sequence still requires real native calls, successful readiness/readback, reference pixels and cleanup. Decoder internals, transport buffering, physical GPU memory and garbage collection remain outside these logical measurements.
