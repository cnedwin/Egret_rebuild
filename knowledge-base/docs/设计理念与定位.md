# 设计理念与定位

[English](设计理念与定位.en.md) | 简体中文

白鹭重构要延续曾经帮助开发者跨越技术时代的能力。过去以熟悉的 AS3 对象、显示列表与事件模型帮助 Flash 团队进入 H5；这次要让创作意图成为能持续修改、验证、交付的游戏工程。第一人群是主要依靠 AI 制作游戏的新创作者，也包括开始依靠 AI 工作的手游开发者。两类人群的学习路径需要分别测试，不能用同一套新手假设代替。

## 已确认的方向

R001 确定服务人群，R002 与 R004 确定复杂 UI 2D 和轻量 3D 的组合，R003 确定渲染运行时的核心地位，R008 确定旧工程迁移的最终交付，R009 确定知识库与社区参与的持续性。完整原意以[需求登记册](../registry/需求.json)为准。

“轻量 3D”尚未等于某个模型数量、材质规格或物理能力。第一批玩法、规模、画质、宿主、设备及性能预算需要一起定义。PC 广泛兼容和大型原生 3D 的优先级尚未作新决定，历史取舍不能直接成为新版本承诺。

## 候选产品定位

面向 AI 新创作者，提供一套对复杂 UI 和轻量 3D 都有清晰预算的游戏引擎与创作工具，让同一作品从初次可玩走向连续修改、多平台交付和长期更新。

这一定义包含三项待验证的差异化：复杂 UI 与混合渲染的持续效率；AI 修改现有作品的可靠性；旧白鹭资产迁移到新体系的低干预能力。市场价值、创作者完成率和性能领先都仍是[验证假设](../registry/假设.json)。

## 设计原则

1. **保留创作者的控制。** 自然语言、可视化编辑和代码操作同一个工程；修改可定位、可预览、可撤销，成功作品可以继续维护。
2. **性能以玩家体验为尺度。** 首次可交互、持续帧时间、输入延迟、内存和功耗共同决定体验；空包体积与平均 FPS 不能单独证明领先。
3. **核心精简，能力按需。** UI、3D 和动画共享必要基础，各自采用合适执行策略；模块、后端、诊断和旧兼容层可裁剪。
4. **接口稳定，内部可替换。** 对象、资源、工程和协议分别管理版本；升级必须携带迁移规则与回归证据。
5. **按问题研究成熟实现。** 记录第三方如何解决问题、适用条件和维护代价，保留来源鸣谢，再选择适合白鹭工作负载的方案。比较采用锁定版本与实际证据。
6. **把交付作为创作的一部分。** 资源、构建、宿主适配、测试和更新形成闭环；具体平台承诺由真实宿主验收产生。
7. **公开设计与验证。** 从第一天按开源方式建设，公开文档、知识库、设计问题与依据；来源、失败记录和未验证边界可供社区审阅。

## 本阶段的判断标准

用同一创作任务比较首次可玩、连续修改后的玩法保持、人工接管次数、修改成本以及实际设备发布成功。让已有经验的手游开发者完成同样任务，观察其需要保留的 API、资源与调试习惯。测量方法见[核心优势与验证](核心优势与验证.md)，技术候选见[技术架构](技术架构.md)。
