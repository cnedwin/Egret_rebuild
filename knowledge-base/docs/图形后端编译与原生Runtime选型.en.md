# Graphics Backends, Compilation Pipeline, and Native Runtime Selection

English | [简体中文](图形后端编译与原生Runtime选型.md)

Version: 0.1 candidate design · Knowledge base: 0.6.1 · Updated: October 8, 2026.

The new Egret is advised to adopt a WebGPU-oriented graphics architecture while maintaining a WebGL-compatible executor. Canvas primarily provides text and offscreen content; limited pure-2D fallback is defined separately. Continue using TypeScript for development, separating fast preview, type checking, resource builds, and native compilation. For the native Runtime, first establish replaceable graphics, scripting, and host interfaces, then introduce Rust module by module according to benefits while retaining mature C++ dependencies. Desktop expansion and GPU AI connect through optional capabilities; every work need not carry all modules.

The objectives are complete-work experience for complex UI, 2D animation, and lightweight 3D, fast iteration, and low loading cost. Historical compilation times added by S033 are historical experience. The names Rust, WebGPU, or a new compiler do not establish present-day performance benefits. Round three's current 17 desktop WebGL2 reference checks retain their scope; this selection research adds neither coverage nor passing checks. Technical candidates still await corresponding product and device acceptance.

## Three development paths

| Path | Benefits | Costs and judgment |
| --- | --- | --- |
| WebGPU-only; browser and native platforms all enter a WASM core | Graphics expression and resource management can be organized readily around modern APIs | Concentrates host coverage, download/initialization, cross-language communication, debugging, and cross-platform text costs; full adoption is not recommended at this stage. |
| Center on legacy WebGL and C++, adding WebGPU incrementally | Carries forward experience and compatibility paths | If public materials, resource lifecycles, and frame contracts remain tied to the old API, new capabilities continually become branch patches. Retain the old implementation for comparison, but do not let it lock the new architecture. |
| Unified work semantics and capability contracts, dual WebGPU/WebGL executors, independent native adaptation | Develops toward new GPU capabilities while preserving market coverage and on-demand package size | Requires semantic, recovery, and quality regression maintenance across backends; recommended candidate direction. |

## Roles of WebGPU and WebGL

WebGPU is the main path for advanced capabilities and future optimization; WebGL is a compatibility path requiring ongoing maintenance. Base the new design on explicit resources, pipelines and binding layouts, render passes, asynchronous device initialization, and loss recovery. Select executors by work and host profile. At startup, test actual adapters/devices, features, limits, texture formats, surfaces, and representative shader initialization; checking only for navigator.gpu is insufficient.

Within one main surface, compose 3D, UI, 2D skeletal animation, and frame animation using the same device and frame scheduler wherever possible. UI in WebGPU mode is also drawn by WebGPU; UI in WebGL mode is drawn by that WebGL context. The [HTML standard](https://html.spec.whatwg.org/multipage/canvas.html#dom-canvas-getcontext) specifies that different context types cannot bind to one canvas simultaneously. Do not default to WebGPU drawing 3D and WebGL drawing UI with a cross-API copy every frame. Multiple surfaces, third-party video, or host-mandated composition are explicit adaptation boundaries.

Canvas can measure and draw text and some vectors on an offscreen surface, uploading changes to the selected GPU backend. Original text, font readiness, atlas generation, resolution, color space, and premultiplied alpha belong to one resource contract. The objective of reducing redraws/uploads through caching still needs measurements on actual text workloads. Canvas does not necessarily mean software execution, and a GPU main view does not automatically solve Chinese fonts, IME, or line breaking.

WebGL targets WebGL2. Limited WebGL1 2D compatibility is included only when target hosts or legacy-project samples actually require it. A Canvas-only profile covers declared 2D features only, not complete 3D, arbitrary filters, or GPU compute. Necessary effects without equivalent implementations block export; optional quality fallback is recorded in the work profile. Select the backend before resource creation. Device loss first recovers the original executor. If fallback is needed, recreate surfaces/resources from rebuildable CPU sources and runtime state; do not claim cost-free hot switching.

[GPUWeb's current implementation status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status), updated October 2, 2026, shows expanded formal support in mainstream browsers by OS, GPU, and version. Driver blacklists, hardware acceleration, secure contexts, and actual adapters still impose conditions. WeChat's official Canvas type declarations and Douyin mini-game rendering documentation currently confirm 2D/WebGL paths. The research did not obtain WebGPU guarantees for them; this does not establish absolute inability to support it. Meta, Discord, and Telegram SDKs/iframes/WebViews likewise cannot inherit all desktop-browser capabilities. See [host and GPU AI research](../evidence/backend-host-ai-research.json).

[Three.js's official design](https://threejs.org/manual/pages/webgpurenderer) already uses WebGPU with WebGL2 fallback, but material and postprocessing migration requires changes. Current descriptions still retain experimental status and boundaries where WebGL performs better in some scenes. This informs direction; it does not establish that new Egret has completed dual backends. A WebGPU version cannot directly copy the previous round's WebGL resetState adaptation: new resource layouts, pipeline caches, command encoders, and device-recovery responsibilities need fresh verification.

## Low-level contracts and room for advantage

Public APIs express scenes, UI order, material semantics, resource references, quality levels, and gameplay events. Backends may have different executors and shader implementations; do not wrap individual WebGL bind/use calls into a public RHI. Kernel interfaces work in stable handles, resource descriptions, passes, and batched commands. Extensions need not all be reduced to the lowest common set of every backend.

Define only Egret's actual supported material-semantic subset and explicit extensions. Arbitrary Three/Babylon materials, TSL nodes, postprocessing, or private objects cannot automatically become native wgpu/Dawn commands. Mature renderers own their internal shaders/caches. Shared devices, passes, resource import, and final presentation require public interfaces and pinned-version verification. If interfaces do not permit this, retain isolation or replace components; do not claim the unified contract already implements general interoperability.

Recommended fixed responsibilities:

- UI and 2D preserve display order and allow merging adjacent compatible batches; complex UI does not become one 3D object per node.
- 3D organizes by depth, materials, and transparency semantics, using compute batching when necessary. Lightweight workloads retain CPU paths to avoid extra synchronization, uploads, and scans merely to use the GPU.
- Resources distinguish CPU sources, decoding, uploads, residency, completion of use, and release. deviceEpoch, resourceGeneration, and instance leases cannot collapse into one ready boolean. Rebuildable sources do not mean retaining all decoded data indefinitely. Budget retention of compressed sources, stable URIs/hashes, and generation parameters. Offline recovery needs offline-accessible sources or an explicit failure status.
- Graphics creation and submission have one owner. Asynchronous pipeline preparation, upload budgets, caches, cancellation, and recovery have diagnosable outcomes. Mature shader tools or selected components handle WGSL/GLSL/HLSL/MSL differences; material contracts still need regression on every backend.
- Browser 2D packages use the host JS environment without a native VM. Native 2D packages still need the selected VM or a verified host VM. Each profile removes unused 3D and AI models; enhanced backends use split packages by target build. Optimization accounts for CPU preparation, GPU work, bandwidth, memory, cold start, and first interaction together.

Potential advantages lie in sparse UI updates, text caches, ordered batches, capability-based builds, asynchronous preparation, and sustained-load control. WebGPU compute, render bundles, and similar features are tools, not optimizations to enable by default in every work. The size of an advantage comes from comparisons at equivalent functionality/image quality on the same devices.

## Compilation and debugging pipeline

New projects should pin current stable TypeScript semantics and tool versions, splitting development iteration into independent pipelines. Source changes first get fast transpilation and local replacement. Background incremental type checking outputs diagnostics for the corresponding project version. Resources convert by content hash. Release stages run full type, capability, resource, and target-build checks. The editor, CLI, and Agent share configurations and structured diagnostics; a visible preview does not imply release readiness.

As of October 8, 2026, both [Microsoft's release list](https://github.com/microsoft/TypeScript/releases) and [published package metadata](https://registry.npmjs.org/typescript/latest) point to TypeScript 7.0.2. The Go native rewrite was [officially released on July 8](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/). Pinning this version is recommended as a candidate CLI/LSP baseline for new projects; the main line should no longer be described as tsgo preview. This native compiler is a development tool. Games still output JS; upgrading does not turn them into native machine code or directly increase runtime frame rate. Official comparisons of roughly 8–12× faster full builds on public projects are vendor measurements and have not been reproduced for Egret.

The artifact chain is TS source → JS and source maps → browser or native script VM. Rust/C++ cores, shaders, and resources compile/convert separately. VM caches/snapshots are produced for that VM, version, build, and architecture; they do not replace the original editable project. Record the time for each step separately.

TypeScript 7.0.2 exposes an unstable new API but provides no stable compatibility guarantee that directly inherits the old Compiler API. An independent TS6 tool process can handle old analysis, code generation, or editor plugins without entering the game package. The 7.1 API stabilization plan is not delivered capability. For Web preview, first evaluate the officially released [Vite8](https://vite.dev/blog/announcing-vite8), with Oxc transpilation and Rolldown bundling. [Its official documentation explicitly says transpilation does not type-check](https://vite.dev/guide/features#typescript). Mini-game publication still uses independent target exporters; do not assume Vite's dev server can move directly into all hosts.

Legacy namespace, ES5/AMD/System configurations, const enum, legacy/standard decorators, and reflection enter migration separately. Vite8/Oxc decorator metadata support has [inference boundaries](https://oxc.rs/docs/guide/usage/transformer/typescript); “supported” must not conceal Object fallback. Where exact legacy semantics are needed, retain appropriate transformation adapters or start with a compatible transpilation path. Prefer explicit schemas/registration for new component metadata, aiding Agent changes and backend exchange. See [compilation toolchain research](../evidence/backend-ts-research.json) for complete versions and unknowns.

Record cold start, one ordinary code change, scene changes, shader changes, incremental type diagnostics, release builds, and native builds separately. A historical project compiling in under 30 seconds cannot become the interaction budget for a new project's single change. Set specific objectives on representative samples and current devices. First avoid rescanning or rebuilding unrelated resources on every change; only then replace measured compilation hotspots.

Hot updates distinguish resources, scene data, module code, game state, and GPU pipelines. State uses explicit schemas and migration; unsafe structural changes perform predictable local or complete restarts. AI-oriented creators cannot be promised preservation of all runtime state across arbitrary code changes. Source maps connect runtime errors to original TS, scene objects, and Agent change transactions; obsolete-build errors must not contaminate current-project diagnostics.

## Roles of Rust and C++

Rust suits new resource-ownership, scheduling, command-validation, and concurrency infrastructure modules; C++ can continue to provide mature graphics, scripting, font, and platform dependencies. Both can produce efficient machine code. Rust's ownership checks help reduce a class of memory and concurrency errors, but do not prove the same algorithm necessarily faster or lower in power. FFI, GPU handles, and external lifecycles still need explicit verification.

The candidate first establishes a narrow C ABI, versioned batch protocols, and explicit thread/buffer ownership, avoiding JavaScript boundary crossings per node and per property. Logical authority stays in TS; native trees and GPU data are rebuildable execution mirrors. Required cross-boundary events have independent identities and acknowledgement rules, and are not cleared with graphics recovery. WASM handles only measured hotspots, accounting for download, compilation/initialization, copies, and bridging. Threads/SIMD depend on host capability; do not automatically bring every browser version into a large WASM module.

A complete Runtime also includes the script VM, surface, input/IME, fonts, audio, networking/files, lifecycle, and debugging. Replacing the GPU library or language cannot directly cover these responsibilities. SDK embedding into an existing App needs explicit host/Egret responsibilities for device/surface, threads, resource synchronization, and loss recovery, preventing both parties from owning submission and reclamation.

A browser Canvas text provider does not directly exist in a pure native Runtime. Native uses an independent text provider to wrap mature system text or candidates such as Skia/HarfBuzz/FreeType, verifying fonts, shaping, fallback, IME, and caches item by item. Share original-text/layout contracts without requiring the same Canvas API on both sides. A WebView wrapper uses that container's actual capabilities and must not be conflated with native SDK acceleration.

## Native graphics and script VMs

Graphics interfaces leave room for modern D3D12, Vulkan, Metal, and other backends. Independent D3D11 execution or integration with an existing host device is evaluated separately. Steam is a distribution and service-integration target. Desktop adaptation also needs windows, input/controllers, files, lifecycle, shader distribution, and platform publication; graphics-API support does not automatically complete these.

First compare Rust wgpu and C++ Dawn for maintenance, backend capabilities, and SDK integration cost. Select one primary implementation and retain replaceable interfaces; do not maintain several complete renderers simultaneously. GL compatibility or bgfx may serve specific comparison needs, without indefinitely stacking all abstraction layers. Record low-level libraries' public support tables, mainline code, and accepted support levels separately; unbuilt code cannot be marked as Egret support.

The [official wgpu backend table](https://github.com/gfx-rs/wgpu) lists Vulkan, Metal, D3D12, and GL, without direct D3D11. Dawn's current mainline has a [D3D11 implementation](https://github.com/google/dawn/tree/main/src/dawn/native/d3d11) and an [interface borrowing ID3D11Device](https://github.com/google/dawn/blob/main/include/dawn/native/D3D11Backend.h), ahead of some README/support tables. Mainline existence does not prove a particular release or Egret build passes. If a native SDK needs an existing D3D11 App, Dawn is a key comparison; if modern backends and Rust management take priority, wgpu is the preferred candidate. Begin with a reviewable comparison scope rather than promising production support for both libraries. GL compatibility, D3D11 integration, and complete modern graphics capabilities are different commitments.

This official release/docs review identified Rust wgpu 30.0.1 and the separate C binding wgpu-native release 29.0.1.1. Their headers/libraries cannot be mixed, nor can synchronized upgrades be assumed. Dawn mainline observations and the nightly release found in this review are recorded separately; mainline files must not masquerade as that release's binaries. The SDK declares owned/borrowed device modes and checks same-device constraints, external resource import, BeginAccess/EndAccess or equivalent synchronization, resource states, fences, submission/release order, and shutdown threads. These backend extensions do not automatically map to browser-standard WebGPU sharing. If direct import is impossible, state copy/composition paths and account for costs.

Archive review identifies the VM in the historical account as V8. Supplementary archives contain several V8 header directories and JSVM adaptation paths. CMake's default conditions select JSVM, while unconditional linkage to precompiled V8 libraries is also visible; the effective VM and binary version require build verification. The highest-version directory cannot be treated as the running version, nor establish an upgrade or speed improvement. Private-item evidence remains in internal materials; the public candidate records bounded conclusions only.

The script VM is an independently replaceable module. V8 suits targets prioritizing modern JS, developer tools, and JIT capabilities. Lightweight interpreters may reduce package size and startup cost but may sacrifice sustained execution and ecosystem compatibility. Judge JSC, Hermes, or host JSVM by actual systems, bindings, debugging, licenses, and build conditions. Updating V8 also needs regression of binding APIs, ArrayBuffer ownership, modules, GC callbacks, Promise/task queues, debugging, and snapshots. Precompiled snapshots/bytecode are not universal assets across VMs, architectures, or versions.

For Android/desktop, a maintained V8 is recommended for initial candidate comparisons; check HarmonyOS against host JSVM interfaces. Evaluate system JSC or permitted execution modes separately for iOS; desktop JIT configurations cannot establish store eligibility. QuickJS/Hermes remain comparisons for explicit package/startup/memory or binding needs, without immediately adding formal support for every VM. Pin actual dependencies, build parameters, release binaries, and security-update mechanisms; record performance and base runtime package tests separately. See the [native Runtime research summary](../evidence/backend-native-research.json).

## GPU AI integration space

Put AI first in creation and builds, using real diagnostics to propose changes to resource compression, LOD, texture atlases, shader variants, and caching strategies. Changes must revalidate behavior, visuals, and actual cost. Per-frame LLM calls stay outside core scheduling.

At runtime, design 3D super-resolution, denoising, and small-model inference as optional services. 3D may render at lower resolution, reconstruct to the target resolution, then draw native-resolution UI. Text, hit testing, and business clocks stay independent. Corresponding profiles provide motion vectors, depth, and history frames where algorithms require them, with regressions for camera cuts, transparent VFX, animation, and UI. Lightweight 3D or CPU-bound works may have no net benefit.

WebGPU compute does not directly expose Tensor Cores/NPUs or imply DLSS access. Adapt GPU inference and native vendor SDKs separately. Evaluate actual saved rendering work against added inference, memory, and bandwidth costs; check image quality, input latency, energy, and model licenses. Optional enhancements default off without benefit evidence.

Begin with specified models and execution providers in [ONNX Runtime Web](https://onnxruntime.ai/docs/tutorials/web/) rather than an independently written inference kernel. GPU/WebNN operator coverage differs from WASM; backend failures need explicit alternatives. WebNN is an independent inference API; WebGPU availability does not establish NPU availability. Native DLSS, FSR, XeSS, and MetalFX each need hardware, driver, API, and input acceptance. For example, [AMD's FSR4.1.1, officially released in June 2026](https://gpuopen.com/learn/amd-fsr-sdk-2-3-blog/), expands to specified RX7000/9000 conditions. Do not retain 2025's RX9000-only condition or apply this condition to all FSR functionality.

[ORT WebGPU's default CPU tensor path](https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html) incurs uploads and readbacks; GPU input/output binding needs explicit configuration. AI provider contracts therefore declare input/output locations, device, buffer owner, completion of use, and release rules. Shared GPUDevice must be negotiated before the first inference session. Resources cannot be taken directly from another device. Device loss cancels corresponding jobs and rebuilds relevant sessions; old-epoch results are not read. CPU fallback counts copies and time in the budget. Sharing a device with the selected renderer requires public interfaces and pinned-version verification; zero-copy cannot be assumed.

## Next reviewable outputs

Retain existing 2D skeletal golden samples, complete 3D characters, and complex-UI tasks; add dual-backend capability/material/recovery contracts and TS development-pipeline samples. For native work, first statically map dependencies and VM build authority, then create two small Rust/C++ cost comparisons and an SDK surface-integration description. Host and sustained-load acceptance completes only when actual devices are available.

Do not start foundational matrices, interpolation, GLTF parsing, font rasterization, or shader compilers anew from scratch. Performance experiments focus on Egret's new adaptations, work scale, cross-boundary costs, and differentiating benefits. Complete execution, continued editing, and real publication after R008/V006 one-click migration always remain required. Legacy decorators, TS versions, and resource semantics belong in migration checks.

Migration checklists also need coordinates, color/premultiplication, masks, and composition order in legacy custom GLSL shaders, filters, and postprocessing. Mature WebGPU renderers' custom-material limitations do not automatically resolve these semantics. Conversion, equivalent replacements, and unsupported items all retain diffs and fixed visual regressions; removing necessary effects cannot be called complete migration.

## Selection constraints for independent implementation

R015 and the [independent implementation and third-party dependency rules](独立实现与第三方依赖规范.en.md) constrain later coding tasks. Implement WebGPU/WebGL execution, UI composition, and resource contracts independently to Egret specifications. wgpu/Dawn, VMs, compilers, fonts, or transcoders may be explicit public dependencies. Three/Babylon/PlayCanvas internals inform research; do not extract them and claim them as the core. If integrated as product libraries, identify third-party attribution and the actual self-written scope. The existing 17 reference results do not establish a completed independent backend.
