## Objectives, audiences, and confirmation boundaries

Enable creators to turn intent into playable game projects that can be continually changed, delivered, and updated. Confirmed project requirements are: the first stage mainly serves new creators using AI to make games while valuing mobile-game developers entering AI creation; support complex 2D UI and lightweight 3D, with the rendering engine/runtime at the core, covering 3D scenes, characters, effects, UI, 2D skeletal animation, and frame animation; complete legacy Egret migration and a continuing knowledge base/community are formal requirements.

The journeys, workbench features, detailed priorities, and benchmarks below are candidate design recommendations. Scale, image quality, minimum devices, initial host order, team, budget, schedule, numerical performance thresholds, and business model are unconfirmed. This does not assign launch order to browsers, WeChat, Douyin, or other hosts. D-series candidate technical decisions do not constitute product approval. R001–R017 own requirement authority. R017 confirms starting local core implementation and gap review without accepting the entire candidate or expanding product scope. R011 requires research verification and self-audit; R012 prioritizes mature open-source principles; R015 requires independent core implementation and explicit attribution of public dependencies. Low-level reuse serves complete works, efficiency, and maintainability; artifacts and evidence confirm implementation and acceptance separately.

New creators need to express gameplay, understand changes, discover problems, and complete publication. Verify whether they understand objects, resources, and recovery entry points. Mobile-game developers need to bring existing code, resources, and production experience into AI workflows. Verify needs for code editing, debugging, resource reuse, and batch operations; expert developers doing tasks on novices' behalf cannot prove novice success.

## Product requirements for low-level reuse

R012 makes mature rendering, text, resource, and animation components the preferred engineering starting point. Creators continue using a unified project/editing flow without choosing glyph atlases, understanding GPU state, or handling low-level library versions. Adoption still requires acceptance of Chinese text quality, interaction, recovery, continued editing, target publication, and old-project comparisons; component features cannot directly be marked complete Egret capabilities. See [open-source reference implementations and adoption plan](开源参考实现与采用方案.en.md) for adoption boundaries.

Round three's real-asset reference chain has executed 3D animation, shared instances, Canvas original text/caches, rendering handoff, and recovery boundaries. It is an R&D input, not a workbench on which creators can complete production. Initialization failure, cancellation/leaving during loading, and repeated startup should return to recoverable states. After visual recovery, verify interaction again before reporting the work usable. Production initial packages are generated by 2D/3D capability profiles; pure-2D works must not carry all 3D reference modules by default. See the [round-three integration record](第三轮集成记录.en.md) and [audit](第三轮审计.en.md) for current boundaries.

## Projects and creator control

A “project” includes editable scenes/UI, objects, original resources/dependencies, business code, gameplay rules, target configurations, and version records. Playtest results and release packages are artifacts generated by the project. Exported projects remain open to production; an unmaintainable package alone is insufficient.

Objects and resources have stable identity. After character renaming, button movement, or resource-path changes, references, change records, and issue locations still point to the same object. Users select by name, image, and purpose without understanding internal identifiers. Copying creates new identity with explicit reference relations; deletion shows affected gameplay and resources.

Natural language, visual, and code editing operate on one project. Business code and source resources can be viewed, changed, retained, and exported. AI changes must not overwrite later manual user edits. Users choose whether temporary playtest state writes back. Each task shows objectives, scope, changes, and acceptance results. AI must not silently delete gameplay, events, resources, saved data, or platform features merely to remove errors. Fallback must explain impacts and obtain a user choice. Failures stop at recoverable versions; cancellation, retry, and undo do not damage existing works.

Round-two research refined event recovery, nested layout, and asynchronous resource contracts. The candidate user behavior/acceptance below builds on that work without adding implemented capabilities. Layout research used external text-size fixtures, resource research manually interleaved tasks, and event research covered only in-memory consumption in living sessions. Mixed graphics programs used procedural meshes, a simple two-segment skeleton, and atlases. Real text shaping, real asynchronous GPU uploads, a complete editor, and migration remain unfinished. The [round-two verification record](第二轮验证记录.en.md) and [audit](第二轮审计.en.md) own actual results, failure history, and omissions.

## New-work journey and core acceptance

Organize the proposed workbench around works, the editing view, resources, playtesting, task records, and publication. Explain flow feedback as “what is being processed, where it is blocked, what already exists, and the next choices,” without burdening creators with model protocols or rendering implementation requirements.

| Step and capability | Specific acceptance scenario | Failure state and user feedback |
| --- | --- | --- |
| Initial creation (R001, R006; V003, V005) | The user describes character display/outfit-change gameplay, confirms a gameplay summary, and generates an editable work. The first playtest switches outfits and retains selection state. Record time from submitted intent to first playability and human assistance. | Contradictory intent or generation failure shows necessary clarification, usable existing parts, and retry, without claiming completion. |
| Mixed presentation (R002–R005; V002, V004) | One screen contains a 3D character, scene effects, complex UI, skeletal animation, and frame animation. Occlusion, input, text, layers, and animation events match agreements, including consecutive operations and recovery. | Missing animation, misaligned clicks, or budget overruns identify visual objects, reproduction steps, and affected experience. Choices such as lower image quality explicitly show visual differences. |
| Consistent layout and clicks (R002, R004; V002, V005) | Longer text increases list-row height. Insertion/deletion, hiding/restoration, or panel reparenting updates relevant ancestors, siblings, and hit areas together. Visible clicks still choose the correct business object; clipped-out objects do not receive them. | Conflicting layout dependencies or rejected changes preserve previous layout/hit state and identify related panels, text, or dependencies. Dropping updates cannot hide misalignment. Real fonts, IME, and virtual-list reuse have separate acceptance. |
| Multiple local modification rounds (R001, R006; V003, V005) | The user first changes button layout, replaces a character, manually edits pricing logic, then asks AI to change effects. Before application, local previews, diffs, and impacts are visible; afterward, existing outfit/pricing/state workflows replay. Undo restores the corresponding usable version and editing continues. | Ambiguous targets show candidates first; manual project changes show conflicts and handling options without applying obsolete results. Regression failures locate this round's changes and permit original-version restoration or further repair. Do not rewrite the entire project, lose manual edits, or merely say “optimized.” |
| Resource import and outfit changes (R004, R007; V004) | Import models, textures, fonts, skeletal/frame animations, and audio; show previews, dependencies, and use sites. Prepare and validate new outfit materials as displayable before switching, retaining character selection and interaction. Cancellation, another outfit change, or exit prevents late old tasks overwriting new selections; shared materials still used elsewhere are not removed early. | Preparation/display failures identify materials, stage, and cause, retain originals and usable old outfits, and permit completion, replacement, or cancellation. If memory prevents retaining both, explain limits and recovery first; do not silently blank the display or report successful switching. |
| Playtesting and location (R003, R005, R006; V002, V003, V005) | Reproduce a failed button or animation stutter, locate objects from the screen with associated rules/resources, and review results under the same input. Performance suggestions correspond to real measurements. | Unreproducible issues state differing conditions and insufficient evidence. Execution interruptions show the last reliable state, diagnostics, and recovery, not just chat errors. |
| Interruption and recovery (R003–R005, R007; V002, V004, V005) | Display “preparing assets,” “restoring the display,” and “ready to continue” distinctly when the graphics device is interrupted during playtesting. Report the work usable only after relevant resources are displayable again and key interactions revalidate. Outfits, layout, and required gameplay state remain correct; completed sounds/rewards do not rerun because graphics rebuild, and unfinished operations are locatable. | “Device available” is not “work recovered.” Asset preparation, display-resource rebuild, and interaction revalidation failures separately identify affected objects and retry/exit options. Do not misuse late results. External services, process restarts, or unconfirmed operations show pending verification, without promising automatic completion or absolute nonduplication. |
| Repair and undo (R006; V003, V005) | AI repairs missing references within user-visible time/cost limits and revalidates original gameplay. Undo restores the project, resource references, and gameplay, after which editing continues. | Reaching limits, cancellation, or semantic uncertainty stops work, lists changed/unchanged parts and remaining issues, and allows takeover, undo, or another option. Failed retries count toward cost. |
| Target publication and updates (R007; V004, V005) | The user selects a declared supported host, completes capability checks/packaging, and playtests on real devices. After gameplay changes, publish a new version and verify startup, foreground/background, resource updates, and saved data that must persist. | Explain unsupported capabilities before packaging. Build, host-service, and channel-check failures are located separately and retain the last usable version. Generating a package does not mean review approval or successful launch. |

## Legacy-project journey and formal delivery

R008/V006 shares acceptance boundaries with the creation loop above, targeting minimal human intervention and perfect execution after migration. Report migration success only after complete comparisons pass within the published support matrix. Out-of-matrix, unverified, and partially passing items display separately. Old Egret3D, custom branches, and third-party SDKs are not automatically supported.

| Step | Specific acceptance scenario | Failure state and user feedback |
| --- | --- | --- |
| Import and inventory | The user selects the original project and creates a read-only snapshot in one click. Inventory engine versions, UI, resources, animation, business code, extensions, and platform dependencies; obtain the old execution baseline and generate a scope report. | Unrunnable originals, unknown versions, or missing dependencies list blockers and handling paths. Preserve original files completely; do not invent legacy behavior. |
| Conversion and repair | Produce an independent new project showing conversion progress, object correspondence, diffs, and AI repair records. Handle remaining issues within published attempt/time/cost limits. | Uncertain rules, exhausted budgets, and unsupported items enter explicit pending-handling states. Do not remove old gameplay to pass builds; allow takeover, rollback, and reruns. |
| Old/new comparison | Under the same input, compare key gameplay, event order/counts, timing/pause/recovery, animation events, layout/hit tests, resource switching/release, saved state, hosts, and performance. Add graphics interruption, resource-preparation failure, and late completion to check old/new semantics and post-recovery side effects. | Difference reports identify original/new objects, business code, or resources, listing reproduction inputs, timing conditions, expected/actual order/counts, mapping rules, and impacts. Duplicate sounds/rewards, missing events, and time jumps fail. Successful startup completes one stage only; external-service doubles cannot replace real-host verification. |
| Continued editing and publication | Modify characters, UI, and business code in the migrated result; complete playtest, undo, target build, and one update. Deliver projects, builds, logs, diffs, unresolved items, and acceptance reports. | Inability to continue editing, missing source assets, broken undo, or blocked publication prevents complete delivery. The original project is recoverable and passing samples enter upgrade regressions. |

## Nonfunctional acceptance and measurement definitions

Numerical targets require baselines from V001's authorized samples with equivalent functionality/image quality and defined host/device/network conditions, then joint agreement. None of the product metrics below is currently measured; local contract/pixel checks are not their baseline. Report distributions, failures, and sample scope together rather than selecting successes or averages. Record creation-task time separately from player time to first interaction.

| Metric | Candidate definition and acceptance approach |
| --- | --- |
| firstInteractive | From a cold-start request to an effective response to agreed player input; separate loading, initialization, and waits, fix cache/network conditions, and check warm starts/recovery. |
| tailFrame | Tail frame times and stutter distributions during sustained playtests, recording sample windows, inputs, and scenes; check input responses too, without substituting average FPS. |
| memory | Runtime peaks, steady usage, and growth after repeated entry/exit/resource replacement; distinguish device conditions and check residues after failure/recovery. |
| Total AI cost | Model fees, calls, caches, retries/failed repairs, tool time, and user waits for a complete creation or migration task; also report total cost per successful task. |
| manualIntervention | Takeover counts, causes, roles, active work time, and waits; necessary account/test setup is recorded separately, and expert repair cannot be hidden as automatic success. |
| Experience and reliability | First-playability time, requirements met, preservation of unrelated gameplay, undo recovery, successful publication/updates, base runtime package/resource loading, sustained power/heat; every metric states its baseline and test conditions. |
| Recovery and semantic preservation | Record three times: resource preparation complete, current display-resource upload complete, and work interactive. Record key pre/post-recovery state, event counts, and unfinished operations. Time objectives await real samples; an appearing image cannot establish complete recovery. |

The migration funnel reports import, conversion, build, execution, complete comparison, and continued editing for all supported projects in the batch, alongside overall rejection rates/reasons. “Zero-manual-intervention success” requires no human code/configuration/resource changes or expert repair and complete passing acceptance.

## Initial benchmarks and questions to verify

The initial main benchmark remains a candidate: complex UI with 3D character display/outfit changes, multilayer panels, scrolling lists, text, skeletal animation, and frame-animation effects, cross-verifying object selection, resource replacement, events, consecutive changes, and budgets. Add a small 3D action scene to verify movement, input, character animation, and effects; action rules/scale remain undefined. For migration, separately select authorized runnable legacy projects covering UI, animation, business state, and platform interfaces. New examples do not replace old projects.

1. What gameplay do new creators first want to make, and can they independently proceed from intent to publication? Where do mobile-game developers need different entry points?
2. What are the initial hosts/devices, which services need real verification, and is offline playtesting sufficient for the first round?
3. How are main-benchmark UI complexity, image quality, asset specifications, and lightweight-3D boundaries fixed, preventing reduced functionality from producing better scores?
4. How do users select local objects, and do they still understand scope/impact after renaming, moving, and copying?
5. Which gameplay must persist across changes, and do previews, conflicts, undo, and regression results let users discover and decide intentional rule changes?
6. Can novices understand asset preparation, display recovery, and work usability? When must pending operations pass to human takeover, and is expert labor hidden?
7. Which code editing, resource tools, and practices are essential entry points for mobile-game developers, and can they share projects with AI?
8. How should old-project versions, extensions, animation, and SDKs be sampled? How is event/clock/resource-recovery equivalence defined, and what happens when old baselines are unobtainable?
9. Can total cost, waits, intervention, and actual-device behavior on equivalent tasks support efficiency differentiation? How does failure cost affect conclusions?
10. Can the community reproduce experiments, propose changes, and understand support boundaries from public documents? Which private assets/authorization limits prevent contributions?

The research portion of V001 is in_progress for organizing samples/baselines. V002–V006 respectively own runtime, project interfaces, resources, creation/publication, and migration acceptance. V002 has a local independent core; other product implementation has not started. V007 continuously maintains requirements, proposals, evidence, and changes; V008 is the candidate design package containing this draft, the white paper, and engineering plan. D001–D016 are all proposed and H001–H008 all untested. Actual checks and fix revalidation in each round remain in corresponding verification records; this draft does not repeat pass counts. R009's community entry should allow reproducible issue submissions and feedback indicating receipt, required evidence, or conclusions. Unreproducible issues must not be falsely reported resolved. R010 competitor research compares costs and selection reasons for equivalent tasks; promotional documentation does not establish product leadership. Scope changes first update requirements/evidence, then update this draft after confirmation.

## Compilation/debugging and native extensions

R013 requires reduced waits after creation changes, with preview, type diagnostics, and release status separately visible. Errors map back to original code, scenes, and Agent transactions; resource changes do not rebuild unrelated content. Historical sub-30-second times are not direct numerical gates for the new product. R014 requires room for native App/SDK and cross-platform expansion; Steam/PC and GPU AI are not launch commitments. Browser 2D carries no native VM; native 2D still needs a selected VM or accepted host VM. Creators need not select Rust/C++ or graphics libraries; the product shows available capabilities, actual errors, and support for necessary effects. See the [selection design](图形后端编译与原生Runtime选型.en.md).

## Community open source and implementation attribution

The project is built as open source from day one, with documents, the knowledge base, and design discussions public to the community. Independent core, third-party dependencies, and research references each state their origins/scope. Write the Egret core independently under R015 and the [independent implementation and third-party dependency rules](独立实现与第三方依赖规范.en.md); AI-assisted development follows the same rules. Wrappers/adaptations of third-party renderers retain accurate implementation attribution. Implementation origins, dependencies, and release notices enter delivery checks. The public repository is cnedwin/Egret_rebuild; first-party code/documents continue under Apache-2.0. Public content needs appropriate authorization. One-click legacy migration, continued editing, and real publication requirements remain.
