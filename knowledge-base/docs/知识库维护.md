# 知识库维护

[English](知识库维护.en.md) | 简体中文

[README](../README.md) 是入口，[当前版本](../当前版本.json) 指向有效资料。状态权威集中在 [需求](../registry/需求.json)、[决策](../registry/决策.json)、[假设](../registry/假设.json)、[交付](../registry/交付.json)、[来源](../registry/来源.json)。本文及其他说明文档不复制全量登记册。

## 更新顺序

1. 登记来源、日期、访问范围与证据；区分官方陈述、观察结果和推断。
2. 关联事实或假设、决策、需求、交付及实验验收，形成“来源 → 事实/假设 → 决策 → 需求 → 交付 → 实验验收 → 新证据”的记录链。
3. 修改受影响的解读文档及版本入口，说明变化原因；保留被替代结论和证据边界。
4. 在知识库根目录的 PowerShell 7 环境运行 `pwsh -NoProfile -File tools\Validate-KnowledgeBase.ps1`，检查编号、链接、引用及敏感内容标记，再由评审人确认内容。工具不抓取外部网页，也不代替内容或授权审查。

候选架构保持“提议/待验证”性质；计划、工具检查通过或文档齐全均不能替代实现验收。新增证据推翻假设时，记录原结论、反证和受影响项目，不静默覆盖。

## 拟议职责与节奏

项目负责人确认范围变更；资料维护者整理登记册；领域评审人核对技术证据；验收人核对可复现结果。角色均待任命，同一人兼任时注明。

每次证据、决策或交付变化后更新，定期复查失效来源、待验证假设与未分配事项；维护节奏和职责在社区治理中登记。R009承载知识库与社区需求，R018确认从开发初期公开协作。按[公开表达规范](开源协作与公开表达规范.md)整理设计过程、来源、讨论和验证记录，发行目录与受权限限制的原始资料分别管理。

## 开源参考的维护纪律

R012及[研究与验证分工](开源实现优先与验证分工.md)确立源码优先：记录完整commit、文件/函数、许可、已修复问题、采用方式、假设及替换条件；当前网页与历史标签分开，不把不同版本拼成同一次实现验证。固定版本源码证明机制，适配实验证明白鹭集成，真实设备证明性能和支持，三者分别记录。

已确定的成熟原理可以推进工程；按R015分别管理显式公共依赖、基于自有规格的独立实现和研究对照。升级上游后检查受影响合同和回归，记录源码阅读、测试阅读与实际测试运行的范围。业务输入及其规范化策略明确登记；历史源码按既有权限管理。

## 实现来源的维护

执行[独立实现与第三方依赖规范](独立实现与第三方依赖规范.md)。每次核心实现或依赖变化同步[实现来源记录](../templates/实现来源记录.md)，说明自写范围、参考资料、显式依赖、AI参与和验证。研究依赖及结果保持原有归属；发行声明、来源评审和技术验证分别维护。

## 公开副本与历史证据

为公开协作整理文字或环境路径时，记录编辑类型、原材料摘要及适用版本；数值结果、技术结论、源码身份与修订事实保持可追溯。历史审阅摘要绑定审阅当时的文件，当前文档演进不扩大其覆盖范围。公开工程提供当前源码与可重复验证入口，发行清单明确包含和未随发行提供的材料。
