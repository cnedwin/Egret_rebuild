# 资源核心实现记录

[English](资源核心实现记录.en.md) | 简体中文

日期：2026-10-08 · 知识库0.11.0 · 产物版本0.0.0 · 支持级别experimental。状态：CPU子集已实现并完成本地验证。

本段在已有三个headless核心包上增加CPU资源获取与租约，公共入口为工作区包`@egret/engine`的`engine.assets`。行为依据[资源核心合同](资源核心合同.md)，它将[公共API合同](公共API设计与命名规范.md)中的类型化引用、获取取消与Scope所有权落实为单独的实现切片。本文记录实际CPU实现及本地验证；结果与来源摘要由[有界验证报告](../evidence/asset-core-verification.json)维护，不代表完整资源产品、图形后端或真实宿主验收。

## 实现边界

contracts增加assets诊断阶段；runtime定义资源类型、引用、provider与租约协议并负责CPU资源管理与所有权；engine负责实例装配与关闭顺序。包依赖方向保持engine → runtime/contracts、runtime → contracts，公共使用和行为验证从构建后的`@egret/engine`入口进入。核心保持无DOM/Node环境全局的边界；Node用于开发验证和示例。

`createAssetType`建立带运行时guard的类型描述符，`createAssetRef`建立类型化稳定引用，`register`为该类型配置provider，`acquire`返回独立租约。类型由引用推断，provider成功结果仍经过guard验证。工厂身份、类型不变性和同一ID的类型绑定共同限制错误引用，不能用调用者填写的泛型代替运行时检查。同名类型描述符不自动共享身份。

provider是CPU值的取得与同步清理边界。每个成功load结果具有独立清理所有权；底层对象需要共享时，provider负责封装自己的引用计数。管理器不提供网络provider、协议下载、图像/模型/字体解码、GPU上传或驻留、预算/LRU、持久manifest、deviceEpoch恢复与在途GPU栅栏。

## 状态与所有权规则

| 对象/操作 | 合同 |
| --- | --- |
| 单次获取 | `waiting → delivered / cancelled / failed`，先成为终态者生效；只有等待中的获取响应其signal。 |
| 已交付租约 | `active → released`；release幂等，之后value访问抛出`ASSET_LEASE_RELEASED`。成功交付后解除获取的取消监听，后续abort不释放租约。 |
| 共享任务 | 同一ID/类型/当前代际共享一次load，每次获取仍有独立租约；取消一个等待者不能中止其他需求。 |
| 无需求代际 | 最后等待者取消且无已交付租约时，先终结entry再通知provider；忽略取消的迟到成功结果只清理、不交付。最后有效租约release后清理，下一次获取产生新代际。 |
| invalidate | 原代际退出后续获取，已有等待者与租约继续持有它；后续获取建立新代际，旧回调/旧release不得覆盖或删除新entry。 |
| 管理器关闭 | 同步关闭入口、拒绝等待、撤销自己的全部租约并清理值；重复dispose幂等。Engine在Scope与Stage清理后、host.stop之前关闭assets。 |
| Scope/Engine归属 | 租约绑定来源Engine；外Engine的Scope接管报`ENGINE_MISMATCH`。Scope先取消等待，再逆序release租约，closed时迟到的无owner租约仍由use清理。 |

`leaseId`与`taskId`在管理器内递增，`resourceGeneration`在同一ID内递增，均为正安全整数。它们的职责不同，也不代表持久工程ID、设备epoch或跨线程ACK。有效ID不隐式trim或改写。

清理与重入遵循先提交终态、再调用外部代码的顺序。entry终态、当前映射移除与清理尝试标志必须先于取消通知、类型guard的后续处置、provider.dispose和诊断回调；删除映射须核对entry身份。每个成功load结果只尝试一次同步dispose；抛错会记录assets诊断，Engine关闭时保留cleanupErrors，其他清理继续。一次dispose调用不等于物理清理成功，忽略取消或永不settle的provider也不能靠同步管理器关闭证明物理工作已停止。

管理器撤销的是租约的value访问权；此前复制出的普通CPU对象引用无法物理收回。调用者应保持租约覆盖所有借用者的使用期。这个边界不能推广为GPU句柄或线程安全保证。

## 调用示例

下例展示类型guard、provider与Scope接管，已对当前构建的公共声明完成strict编译，未引入DOM/Node环境类型。它是CPU对象样例，无外部句柄、网络请求或解码；实际异步执行另由下文的文件provider样例验证。`HostAdapter`由调用者提供，真实宿主适配须另行验收。

```ts
import {
  createAssetRef,
  createAssetType,
  createEngine,
  type AssetProvider,
  type HostAdapter,
} from "@egret/engine";

interface Caption {
  text: string;
}

const captionType = createAssetType<Caption>(
  "caption",
  (value): value is Caption =>
    typeof value === "object" && value !== null &&
    "text" in value && typeof value.text === "string",
);
const welcome = createAssetRef(captionType, "screen/welcome");

const provider: AssetProvider<Caption> = {
  async load(ref, { signal }) {
    await Promise.resolve();
    if (signal.aborted) throw signal.reason ?? new Error("Cancelled");
    return { text: ref.id };
  },
  dispose(value) {
    // This plain CPU fixture has no external handle to release.
    void value;
  },
};

export async function readWelcome(host: HostAdapter): Promise<string> {
  const engine = await createEngine({ host });
  const screen = engine.createScope();
  try {
    engine.assets.register(captionType, provider);
    const caption = screen.use(await engine.assets.acquire(welcome, {
      signal: screen.signal,
    }));
    return caption.value.text;
  } finally {
    screen.dispose();
    await engine.dispose();
  }
}
```

需要长期保留资源时保持租约；不要把上述函数退出后的租约当作仍有效。获取成功后，screen的signal再abort只影响仍在等待的获取；本例最终由screen.dispose释放已登记租约。provider应在真实工作边界响应signal，管理器仍负责识别并清理已被放弃的迟到结果。

## 失败与诊断

获取入口的关闭、无provider、伪造引用、类型冲突、取消、load同步抛错或异步拒绝，以及guard失败/抛错，通过拒绝Promise交给调用者。失败代际终结，后续显式acquire可以重试；没有隐式重试。验证失败的已返回值仍进入清理。管理器观察所有内部Promise拒绝，调用者仍须处理自己的acquire Promise。

工厂、register与invalidate的检查失败同步抛出；acquire把入口与异步失败转为拒绝Promise。当前代码中的资源错误如下，测试覆盖范围仍以实际运行报告为准。

| 错误码 | 触发条件 |
| --- | --- |
| `ASSET_TYPE_INVALID` / `ASSET_REF_INVALID` | 无效名称/ID、非工厂类型描述符或伪造引用。 |
| `ASSET_TYPE_MISMATCH` | 同一管理器内已绑定的ID改用另一个类型描述符。 |
| `ASSET_PROVIDER_REGISTERED` / `ASSET_PROVIDER_MISSING` / `ASSET_PROVIDER_INVALID` | 重复登记、未登记对应provider，或load/dispose不是函数。 |
| `ASSET_MANAGER_CLOSED` | 管理器或来源Engine已关闭入口。 |
| `ASSET_ACQUIRE_CANCELLED` | 获取等待被signal取消；取消原因保留为cause。 |
| `ASSET_LOAD_FAILED` | provider load同步抛错或异步拒绝，保留原cause。 |
| `ASSET_VALUE_INVALID` | guard返回false或抛错；抛错时保留cause，已返回值仍清理。 |
| `ASSET_SIGNAL_FAILED` | signal属性读取、监听登记或移除失败。 |
| `ASSET_ACQUIRE_FAILED` | 获取/租约建立中的其他非EgretError失败被包装，保留cause。 |
| `ASSET_ID_EXHAUSTED` | 递增身份将超出安全整数范围。 |
| `ASSET_LEASE_RELEASED` | release或管理器撤销后读取value。 |
| `ASSET_MANAGER_FACTORY_REQUIRED` / `ASSET_LEASE_FACTORY_REQUIRED` | 绕过私有构造器与内部创建凭证；正常调用从Engine获取manager并通过acquire获取租约。 |

`ASSET_NO_DEMAND`是provider signal中的无需求取消原因，不是成功交付后的租约撤销通知。跨Engine的Scope接管继续使用`ENGINE_MISMATCH`。provider清理抛错产生`ASSET_CLEANUP_FAILED`诊断；signal失败也记录诊断，均使用`phase: "assets"`与原cause。取消signal适配器登记/移除监听失败须回滚本地等待，诊断observer抛错不改变清理进度。Engine关闭收集失败，最终关闭错误的首个失败位于cause，其余失败按顺序保留于只读cleanupErrors；不能仅检查cleanupErrors就判断关闭过程没有错误。

固定开发环境为Node.js 24.19.0、pnpm 11.25.0、TypeScript 7.0.2，当前执行为Windows x64的Node headless验证。`node tools/verify.mjs`顺序执行构建、包边界、类型与行为检查，出口为0。实际环境、命令、结果、修订和摘要见[资源核心验证证据](../evidence/asset-core-verification.json)。73包含本次复跑的44项既有回归，新增资源行为为29项；原首段44项与11项负类型断言的历史证据仍保持原身份。研究模型的25例不与本次执行相加，独立审阅探查也不作为新增产品能力数量。

测试先于资源API实现：初始14项基础和12项交错用例在“类型化资源API尚不存在”的前置断言失败。这只证明API缺失的真实红态，不能声称每个嵌套行为分支都曾单独见证失败。第一次实现验证为68/70；两项新测试只检查cleanupErrors而漏掉既有主失败cause，随后按`[cause, ...cleanupErrors]`修正判定，生产错误顺序不变。

后续自查发现signal getter抛出应用EgretError时被直接传播，遗漏`ASSET_SIGNAL_FAILED`包装与诊断；单项机制回归先失败，修订后通过。独立代码审阅又发现登记虽保存函数身份，`load.call`/`dispose.call`仍会读取函数对象后来被改写的自有call属性，破坏登记时固定回调的合同。load与dispose分别增加机制回归，两个用例先失败；改用`Reflect.apply`执行已保存函数并保留原provider接收者后，两个用例通过，完整套件达到73/73。修订前审阅摘要和修订后代码摘要分别保留，不把早期通过报告改写为已包含修复。

尚未执行GPU渲染器、真实浏览器/小游戏/移动设备、Native、字体塑形或文字渲染、生产网络provider、图像/字体/模型解码器、性能/包体/内存/电耗基准或完整旧工程迁移验收。CPU合同通过后仍只推进局部核心实现，不改变完整产品验收与持续编辑、目标发布和更新的义务。
