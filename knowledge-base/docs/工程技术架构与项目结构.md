## 1. 推荐方向与设计理由

推荐采用“分层包 + 熟悉的对象 API + 数据化执行核心”的 TS/Rust monorepo。亲切感保留在游戏语义：显示对象、显示列表、事件、舞台、资源与动画；现代化落实在模块、所有权、工程合同、工具反馈和按目标构建。无需把全部场景改成 ECS，也无需让每个浏览器作品承担完整 Rust/WASM 或原生 VM。

| 结构方法 | 好处 | 主要代价 | 候选判断 |
| --- | --- | --- | --- |
| 全局 namespace + 一个 engine 大包 | 旧团队最熟悉，初期入口少 | 隐式全局与平台条件容易渗入所有层，资源/工具/后端难隔离，按需裁剪难审计 | 仅作为迁移兼容入口，不作为新工程权威结构 |
| 每个功能独立包 + 全 ECS/全 WASM | 隔离强，适合较大团队和部分重数据负载 | 首期包、桥接、任务和发布数量过多，UI 语义与调试成本增加 | 有实测与独立消费者时再拆，不先为所有未来功能建包 |
| 少量职责包 + 内部目录分域 + TS 对象接口/紧凑帧数据 | 对开发者熟悉，工具可共用语义；后端和宿主可替换，渐进下沉热点 | 需要严格依赖与数据权威规则 | 推荐候选 |

这里“成熟数据化核心”指采用脏队列、批量资源变更、紧凑渲染列表、代际句柄等机制；具体结构与执行合同按白鹭规格独立设计，研究来源与第三方依赖分别登记。R015 的独立实现边界继续适用。

## 2. 首期目录与包预算

目录和包名称均为待评审候选；公共 npm scope 的实际可用性未核实。先建立 9 个 TS 工作区包、3 个公共包身份；编辑器和 MCP 作为应用，宿主适配器先在包内分目录，不为每个平台立即建立独立发布包。Rust 的 3 个候选 crate 只在原生阶段确有职责时创建，不意味着本轮建仓或全量 Rust 选型通过。

```text
egret/
  apps/
    editor/                   # 场景、UI、资源、动画编辑器及试玩壳
    mcp-server/               # 发现/调用工程服务的薄适配应用
    preview/                  # 本地可控试玩与诊断 runner
  packages/
    contracts/                # private：版本化 schema、句柄/诊断/宿主与帧合同
    runtime/                  # private：逻辑场景、UI、动画、资源租约、执行提取
    graphics/                 # private：帧计划、资源驻留、WebGPU/WebGL 执行器
    hosts/                    # private：web/minigame/native 接入和平台服务
    engine/                   # public：开发者 API 门面与实例装配
    project/                  # public：工程文档、命令、事务、引用与版本 SDK
    toolchain/                # private：导入、变体、缓存、诊断、目标导出
    cli/                      # public：工程服务命令入口
    legacy/                   # private：旧工程解析、转换规则和对照报告
  native/
    crates/
      egret-core/             # 纯原生基础：句柄、缓冲、协议校验与受测任务
      egret-runtime/          # 原生图形、VM、host 的模块化装配
      egret-ffi/              # 对外 SDK 的窄 C ABI/owned 与 borrowed 接入
    dependencies/             # 显式第三方版本、构建脚本、声明与补丁记录
  examples/                   # 公开可复现作品与教学工程
  tests/
    contracts/                # 格式、事务、协议和所有权不变量
    integration/              # 混合语义、恢复、装卸与迁移对照
    fixtures/                 # 有来源、版本与权限的基准样本
  benchmarks/                 # 性能方法、场景和环境记录
  tools/                      # 仓库开发/生成/依赖边界检查
  docs/
    adr/                      # 提案、接受、取代与实际证据
    api/                      # 从公共 API 生成的手册
```

公共包名不代表 npm 已注册或包已发布。发布入口候选为 `@egret/engine`、`@egret/project`、`@egret/cli`。其余包明确 private；`packages/engine` 内子路径可提供 `/eui`、`/scene3d`、`/animation`、`/web`、`/compat`，但不把每个子路径变成一个必须独立升级的 npm 包。子路径边界需通过目标发行包实际核验；“用了 ESM”不自动证明无用模块、字体、VM 或 3D 资源已裁掉。

拆包触发条件为独立使用/维护责任、不同发布周期、真实隔离需求或实测构建收益。只有文件数量增长不触发拆包。运行时能力扩充优先以目录和 provider 扩展，避免首期出现几十个长期锁步发布的空壳包。

## 3. 模块依赖 DAG

以下箭头表示“依赖”：

```text
engine    -> runtime, graphics, hosts, contracts
runtime   -> contracts
graphics  -> contracts
hosts     -> contracts
project   -> contracts
legacy    -> project, contracts
toolchain -> project, legacy[可选], contracts
cli       -> project, toolchain
editor    -> project, toolchain；试玩沙箱单独使用 engine
mcp-server-> project, toolchain
preview   -> engine；开发诊断通道连接 project/toolchain
```

禁止 runtime/graphics/hosts 依赖 project、toolchain、editor、CLI、Agent 客户端或 legacy 迁移器。禁止 project 回依赖 toolchain，否则工程命令需要构建实现、构建实现又需要工程命令。禁止 graphics 导入运行时显示对象；runtime 输出 contracts 中的值类型/句柄渲染数据，graphics 消费这些数据。禁止 WebGPU provider 直接调用 WebGL provider 或反之。

纯 contracts 层不触发 DOM、GPU、文件、网络、线程、定时器、VM 初始化或全局注册。类型合同与需要执行的校验器分别导出；打包时不因公共类型导入而自动带入全部工程 schema 校验器。持久化 JSON schema、协议 schema 与生成 TS/Rust 类型具有一个源文件权威，生成产物可重建，不能分别手改两份合同。

package 依赖图不表示每个 export 都导入全包；根入口仅保留createEngine与基础2D类型；stage通过Engine实例访问，不自动导入 native、3D 或 EUI。`/web` 完成浏览器 host 与 WebGPU/WebGL 执行器装配，`/scene3d`、`/eui`、`/animation` 是显式构建出口/能力边界。实际是否拆成独立发布包，后续按消费者和版本节奏决定。公共包名和子路径均待登记册可用性与 API 评审确认。

宿主能力通过端口注入，避免每层判断“是不是微信/安卓”。性能热点允许明确的内部扩展口，但不能以随意 `internal` 导入绕过资源代际、设备 owner 或持久化格式版本。

## 4. 各层职责与数据权威

| 层 | 拥有的事实 | 负责的事情 | 不承担的事情 |
| --- | --- | --- | --- |
| project | 版本化工程、稳定 ID、场景/资产引用、目标 profile | 查询、原子事务、冲突、撤销、格式升级与结构化诊断 | 不控制试玩中的每帧游戏状态，不直接分配 GPU 资源 |
| runtime | 实例游戏状态、场景语义、UI/动画状态、事件消费身份、CPU 资源租约 | 保留式 UI、命中与布局、动画事件/采样、取消与有界任务、提取执行数据 | 不把 GPU 或原生镜像当第二份业务权威，不调用 LLM |
| graphics | 某一 device epoch 下的 GPU 驻留与执行计划 | 上传、pipeline、pass、合成、使用完成与回收、丢失重建 | 不决定游戏规则或以全局排序破坏 UI/骨骼顺序 |
| hosts | 宿主 surface、生命周期、平台输入/IME、时钟、存储与系统服务合同 | 真实能力协商、错误分类、平台 SDK 适配 | 不假造完整浏览器、不隐式降级必要玩法 |
| engine | 一次运行实例的装配和生命周期 | 公共对象 API、统一设备/时钟/资源所有者、启动/暂停/恢复/关闭 | 不成为全局服务定位器，不泄露未稳定后端实现 |
| toolchain | 对特定输入版本产生的派生产物 | 资源转换、shader 变体、内容哈希缓存、目标模块/分包清单、构建诊断 | 不修改工程作为构建副作用，不视缓存为源资产权威 |
| editor/CLI/MCP | 用户意图和操作界面 | 调用同一工程/构建服务、显示差异与等待、查询/取消任务 | 不各写一套引用检查、资产导入或改文件协议 |
| legacy | 转换规格和转换报告 | 解析旧工程、确定规则、辅助 AI 修复、行为/视觉/发布对照 | 不把旧工程或第三方运行时永久引入每个新工程 |

持久化对象/资产 ID、运行实例句柄、GPU 句柄、异步任务 ID、deviceEpoch 和 resourceGeneration 分开。稳定名称/路径不是身份；原生指针不能直接作为文件 ID。JS 与原生整数宽度、字节序、包长度和溢出处理写入协议，不依赖“双方刚好使用同一种语言数值”。

## 5. 渲染与后端职责

WebGPU 是现代资源/pipeline/pass 设计主线，WebGL2 是需维护的兼容执行器；WebGL1 仅随目标宿主/旧样本证明的必要性评估。一个主 surface 内 UI、2D 和 3D 由选定后端共享设备与帧调度，不默认每帧在 WebGPU、WebGL 和 Canvas 间交换整张主画面。

Canvas provider 用于文字、部分矢量及离屏内容；缓存变化后上传到选定 GPU。Canvas-only 是明确的有限 2D profile，不承诺完整 3D、任意滤镜或 compute 回退。原生文字采用系统或选定公共字体/塑形依赖 provider，共享文本与布局合同，不依赖浏览器 Canvas 存在。

graphics 内首先按职责分 `frame/`、`resources/`、`pipelines/`、`passes/`、`backends/webgpu/`、`backends/webgl/`。UI/2D 有序列表与 3D 列表来自不同提取路径；共享帧资源、颜色与合成合同。简单帧计划可缓存；多 pass 效果有预算，不能因为资产称为“组件”就假定只需一次绘制。

原生图形 provider 使用一个经过比较的主底层库，通过其公开接口接入；wgpu/Dawn 二者尚未接受选择，不预先生产支持两套完整 renderer。Rust 先进入所有权、任务和批量协议等边界清楚的模块；WASM 热点必须计下载、初始化、复制与恢复成本。浏览器发行包不携带原生 VM。

每个surface默认有独占呈现owner，第二个Engine绑定同一surface须拒绝；只有host明确声明并验收的共享调度模式可例外，首期不默认启用。多个实例借用同一device时，宿主owner统一提交/epoch/生命周期仲裁，不能独立重配置共享surface。设备提交与释放有单一owner。SDK 借用 device 模式声明线程、surface、外部资源状态/同步、完成与归还；丢失时协调恢复，禁止效果组件暗中领取第二台 device 并继续提交。跨 API 或跨 device 的复制路径在 adapter 中明示，并记录成本。

## 6. 宿主边界

hosts 首期按环境而非营销平台拆：`web/`、`minigame/`、`native/`。小游戏目录再分微信、抖音等实际 SDK；Meta Instant Games、Discord 与 Telegram 保留各自 SDK 生命周期/容器能力，不按“都像网页”继承桌面能力。

HostServices 候选包含 surface/输入与 IME/时钟/网络和文件/存储/音频/生命周期/权限/诊断。能力 profile 区分 supported、unsupported、probe-failed、permission-required，并记录所核查的版本；API 存在不等于行为与性能已认证。基线不依赖共享内存或后台线程。支付、社交、广告、Steam 等发行服务属于目标插件，不进入帧循环与纯渲染合同。

原生 Runtime 必须同时解决 VM 任务队列、GPU、字体、输入、音频、文件、生命周期和调试。JS VM 可替换接口围绕模块、Promise/微任务、ArrayBuffer、GC/外部资源和调试建立；并不同时承诺所有 VM。iOS、鸿蒙、Android/桌面按实际运行条件独立验证，不从某个桌面 JIT 基线推导其它平台可用。

## 7. 编译与 Agent 工程链路

普通 TS 修改先快速转译/预览；类型检查独立增量执行，诊断绑定源版本。资源/shader 按输入哈希、转换工具版本和目标 profile 缓存；发布执行完整类型、引用、能力、资源与目标导出检查。原生编译是另一任务，不阻塞每一次仅改变 UI/逻辑的预览。

project 的命令 SDK 是编辑器、CLI 与 MCP 共用的工程接口。MCP 的工具发现、输入/输出转换和权限提示不进入游戏运行包。每个修改事务含版本前提、操作范围、差异、来源与撤销语义；长任务含 taskId、查询、取消、超时、幂等或明确重试规则。新任务取消或旧任务迟到不能把过期产物覆盖到当前版本。

编辑器试玩使用 engine 的真实 runtime，不另造“只在编辑器能跑”的场景解释器。编辑模式控制手柄、选择框等开发装饰，通过可裁除诊断/overlay 接口接入；试玩临时状态只有显式应用后才能写回工程。

AI 输出自然语言建议、工程差异或业务 TS；验证服务保留发布资格、结构/类型/引用和玩法测试判断。编译成功不能代替玩法验收，自动修复必须保持无关功能并受轮数/成本限制。

## 8. 旧工程兼容与现代 API

保留熟悉的语义名称是首选，而非保留全局脚本加载、隐式 stage/singleton 或每层大量 dollar-prefixed 内部入口。公共 TS 对象 API 可继续有 DisplayObject/DisplayObjectContainer/Sprite/Bitmap/TextField/Stage/EventDispatcher 等语义；2D/3D/UI 的扩展通过命名与模块边界消除同名歧义。最终命名由 API 规格统一。

新工程默认 ESM、createEngine 显式实例/依赖、stage 熟悉入口与 await 生命周期。资源Lease、事件on(signal)与Scope遵循[API生命周期合同](公共API设计与命名规范.md)。signal只取消尚未交付的资源等待；已交付租约由release/Scope处理。removeChild只移出树，终结操作使用dispose。可提供 `import * as egret` 的亲切入口，日常教学优先命名导入；它不创建隐式全局。旧 namespace/global 脚本、旧装饰器和事件细节通过可裁剪 compat 入口或迁移器处理，不能反向决定新运行时内部结构。

legacy 是开发时转换器，不是第一发布版迁移目标的替代。若需要临时运行兼容入口，放在 engine 的显式 `/compat` 子路径；不能让 legacy 的项目转换依赖进入常规游戏包。迁移成功需证明显示/坐标/事件/时钟/遮罩/EUI/动画语义、资源、平台发布与后续修改保持；R008/V006 范围与依赖继续保留。

## 9. 公共 API 和扩展治理

公共导出应有明确支持等级：stable、experimental、internal。默认 export 只暴露稳定/已标注实验入口，不以所有文件 barrel export 偶然扩大 ABI。internal 不写入用户工程序列化或文档示例；breaking 变更按公共语义、文件格式、资源合同和桥接协议分别判定，不能只看函数签名。

每个 optional 模块声明初始化/销毁、能力要求、资产 schema、资源预算与退路。注册显式执行，不能靠 import 副作用注册所有 renderer/VM/字体。公共插件使用版本化 Extension API；原生 SDK 扩展和工程插件扩展分别建合同，不能提供任意覆盖 engine 私有对象的通用 monkey patch。

公共包可统一版本便于首期管理；engine 版本、工程文件/资源 schema、协议和依赖底层库版本仍分别锁定，不用一个“引擎版本”掩盖全部升级。stable API 变化提供弃用和迁移信息；experimental 变化显式列出，不能承诺无限兼容。

## 10. 实施顺序与验证

1. 固化包边界、合同权威、公共 API 名册和自有样本；不先创建所有 future provider。
2. 将已实现的纯 TS headless核心接到一个浏览器后端，形成独立实现最小链；保留现有第三方链作机制/正确性对照并标明其实现归属。
3. 接入工程 SDK、导入/构建服务和编辑器/CLI/Agent 共用反馈，完成多人/多 Agent 版本冲突与撤销。
4. 在相同场景下增加第二后端并验证能力/质量/恢复；UI、骨骼、3D 与文字逐项补齐。
5. 再以实际瓶颈评估 WASM/原生模块与 SDK；旧迁移规格全程参与，完整迁移在 V006 验收。

验证对象包括依赖 DAG/禁止反向引用、公共导出快照、schema 与代码生成一致性、最小 2D/混合/原生目标包成分、多个 engine 实例隔离、关闭与失效代际、旧异步结果、设备恢复、等功能等画质对照、AI 连续修改和旧工程完整迁移。本文只定义后续门槛，不声称这些检查已执行。性能数字、首批平台和团队工期仍未确认。
