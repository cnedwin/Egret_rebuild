# Lessons from Shaders and Playground for Egret

English | [简体中文](Shaders与Playground产品技术启发.md)

Version: 0.1 research draft · Verified: October 8, 2026 · Knowledge base: 0.6.2

These products offer references for composable effects that an Agent can understand, and for creation, playtesting, modification, publishing, and discovery. Egret should connect these activities to one maintainable project while continuing to focus on complex 2D UI and lightweight 3D. Every design below is a candidate idea. This round examined official material and pinned source only; it did not install or run the products, generate games, test performance, or implement product features.

## Effects should become project assets

An independently designed Egret effect-asset contract is proposed: stable IDs and versions; parameter types, ranges, and defaults; input resources; color and alpha conventions; blending and mask order; execution capability requirements; preview samples; provenance; and compilation diagnostic mappings. Editor panels, Agent interfaces, and runtime should share this contract. Effects tuned by developers and modified by Agents should belong to the same project.

For example, for “make the golden card-draw glow softer without obscuring the text,” the Agent should locate the existing glow effect, modify its intensity, extent, and composition order, show the result, and retain undo history. The default path selects verified effects and adjusts parameters, with custom shaders as an advanced capability. Retrieval should return a small set of relevant components, parameter explanations, and previews, reducing invented APIs. Shaders' [MCP](https://shaders.com/docs/guide/mcp), [CLI](https://shaders.com/docs/guide/cli), and [Agent reference](https://shaders.com/docs/guide/agent-skill) demonstrate documentation, retrieval, code output, and protection for manual edits working together. These tools were neither connected nor executed in this round.

Egret should also provide an effect-cost contract: which parameters update only uniforms, which rebuild a pipeline, expected passes and intermediate textures, and capability requirements. Actual timing must come from measurements. Depending on target capabilities, choose Egret's own WebGPU/WebGL implementation or explicitly use a compared simplified effect, baked image sequence, or other fallback. Automatic WGSL translation does not guarantee equivalent compute or multipass effects on another backend. Egret core should centrally manage the GPU device, frame scheduling, resource generations, and final presentation. Effect components must not silently switch devices after device loss. CPU Canvas remains subject to the existing text and compatibility boundaries.

This relates to D009 resource specialization and D011 diagnostics. Shaders supplies an effect-asset and toolchain research reference; Egret's rendering core is independently implemented against its own specification. Under R015 and the [independent implementation policy](独立实现与第三方依赖规范.en.md), establish the Egret specification before implementing independently. Explicit public dependencies can be evaluated separately while preserving attribution. Curated Pro content cannot enter Egret's public effect library on the strength of the MIT software announcement. Open foundational components paired with paid curated content/services offer a commercial structure to study; this round does not determine Egret's pricing model.

## From a first playable result to sustained creation

Candidate onboarding path: describe an idea → choose a playable template → play immediately → select an object and request a local change → inspect the change, playtest, or undo → save the project → publish an update. The UI tree, state, resources, and code should be advanced entry points, without requiring new creators to learn rendering pipelines first. Visual tools and the Agent must edit the same project, reducing the cost of moving generated work into a separate maintenance process. This relates to the [AI engineering interface](AI创作与工程接口.en.md) and D012's version contract.

Playground's separation of private drafts and public releases is useful: generation can be cancelled, the stable release continues to run, and an update is published only after user confirmation. Acceptance of an Egret work should cover concrete interactions, state, and resource regressions together; compiling to a playable result does not establish that requirements were met. Sharing and feedback can help creators finish works, but the first stage need not also build a large social platform, asset marketplace, and general high-end 3D creation platform.

Conversational generation, ongoing editing, and source export are already a competitive baseline supported by official material. Future Spark also brings professional 3D and asset ecosystems into the competition. These features alone cannot be presented as Egret advantages, nor can competitors be said to lack complex UI because of technical debt without verification.

## Differentiation must be tested with comparable tasks

| Advantage Egret intends to establish | Future validation, all unexecuted |
| --- | --- |
| Complex UI, 2D animation, and lightweight 3D coexist and remain maintainable through repeated changes | Make 20 rounds of changes to works built to the same brief. Count requirements completed, unintended edits, regression failures, manual repairs, and total time. |
| Mini-game loading and runtime experience | On specified hosts and real devices, compare equivalent functionality and visual quality for initial package size, first playable time, frame-time distribution, memory, and energy use. Shaders source cannot establish performance. |
| An independent open core and project autonomy | Verify local builds, model replacement, project export, and continued editing. Open-source intent does not mean an open-source product has been released. |
| Complete migration of legacy Egret projects with continued creation | Under R008/V006, compare UI, animation, events, resources, and platform behavior in real projects, then complete continued editing, real publishing, and updates. See [legacy project migration](旧工程迁移.en.md). |

The next proposed research round should refine the effect-asset contract, testing parameter and backend boundaries with masked glow, local blur, and image-sequence overlays for game UI, then include them in one multiround creation task. These remain research recommendations to refine; they add no confirmed delivery or budget. D entries remain proposed, H entries remain untested, and V002–V006 implementation and acceptance states are unchanged.
