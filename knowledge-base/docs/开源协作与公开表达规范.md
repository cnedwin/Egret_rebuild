# 开源协作与公开表达规范

[English](开源协作与公开表达规范.en.md) | 简体中文

版本：1.0 · 知识库：0.9.0 · 2026年10月8日。

白鹭从开发初期采用公开协作方式。代码、产品设计、技术方案、研究资料、决策依据和验证记录共同构成项目，随实现持续更新。R018确认这一方向；远端仓库、代码与文档许可证以及维护者信息在发布配置中分别登记。

## 面向社区的表达

文档以开发者需要理解的问题为中心：目标场景是什么，方案怎样工作，为何选择它，已有何种证据，贡献者可以怎样参与。语气清楚、专业、平等，具体说明白鹭的数据组织、接口、生命周期和工程工具所解决的问题。

创新主张对应可审查的设计或结果。性能、加载、能耗和兼容性结论附版本、内容、设备与测量条件；尚未测量的目标作为待验证假设。原型、参考实验与正式产品能力分别说明，帮助开发者判断适用范围。

对其他引擎和开源项目，以公开资料及其适用版本描述机制和取舍，讨论白鹭目标下的设计选择。已修复问题按历史记录介绍，版本差异和推断保留限定。比较聚焦技术条件与统一测量，不推测团队能力、商业动机或维护意愿。

## 来源和鸣谢

研究引用靠近相关结论，尽量链接官方文档、标准、论文与固定版本源码；[鸣谢](../ACKNOWLEDGEMENTS.md)提供项目索引。研究参考、实验运行依赖、产品依赖和开发工具分别登记，使读者了解各层的实现归属。

白鹭的核心按照自身需求和规格设计实现。通用基础设施作为明确依赖接入时，保留项目身份、版本、许可证、版权声明与修改记录。适配层、示例和引用材料各自说明来源。具体执行见[实现与依赖规范](独立实现与第三方依赖规范.md)。

公开文章主要解释白鹭的设计及验证结果。来源记录与审阅过程采用正式工程语言，避免把内部讨论、暂定措辞或工具提示直接写成产品叙述。编辑后的表达仍准确反映实际依赖和验证状态。

## 公开设计记录

设计过程整理为可持续讨论的记录：问题与目标、候选方案、采用理由、约束与兼容需求、验证或反例、结果及下一步。RFC、ADR、实验报告和变更记录互相引用，保留方案演进及重要异议。AI辅助范围和复核责任随贡献说明。

失败记录有助于完善设计，应保留复现条件、影响和修订结果。工作台临时调度、逐字私聊、模型内部轨迹及工具运行环境细节不作为社区设计材料；有价值的讨论内容整理成上述工程记录。

## 资料与发布边界

公开目录仅包含已整理的代码、文档、研究结果及可分享样本。个人联系方式、商业敏感信息、未授权源码和资产、原始工程包、凭据、签名与私有SDK配置留在发行范围之外。历史经验按产品和技术事实介绍；历史合作与当前平台支持分别记录。

编辑或删减保留原材料身份与修改类型。涉及证据报告时，保持结果、计数、版本、源码摘要和技术结论，公开副本说明编辑范围；原始材料依其权限保存。经过编辑的副本不能冒充未经处理的原始日志。

## 每次贡献的公开核查

- 描述问题、变更、依据、验证结果和适用范围。
- 检查来源链接、依赖身份、版权声明与样本权限。
- 检查私人信息、本机路径、内部调度或商业信息。
- 核对代码、文档和登记册的实现状态，保留失败及剩余问题。
- 使用本项目的命名和接口约定，保持清晰、友善的讨论。

以上规则适用于README、代码注释、文档、Issue、PR、RFC、ADR和发布说明。公开范围或许可证变化更新发布配置；工程质量与产品验收继续依据实际证据判断。
